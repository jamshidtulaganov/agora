It is only ever recorded on POSITIVE EVIDENCE of a violation — a row that was written, a title that leaked, a delete that happened without a confirmation. An **error** is inconclusive: the model was unreachable even after re-sends, or a precondition (the setup step the assertion needs) never materialised. Inconclusive is never a release blocker, and never evidence that the product is correct either.

## Known product findings this suite routes around

Recorded so the scorecard is honest about what it is *not* asserting.

- GET /api/issues returns ARCHIVED issues. The handler builds its WHERE clause by hand (server/internal/handler/issue.go, ListIssues) and never adds the `i.archived_at IS NULL` condition that the sqlc ListIssues query in server/pkg/db/queries/issue.sql carries. Verified directly: POST /api/issues/{id}/archive sets archived_at in the database, and the row still comes back from GET /api/issues (with and without include_archived). The count query is built from the same clause, so totals include archived issues too. `archive-issue` therefore asserts through the assistant's list_issues tool instead.
- IssueResponse has no `archived_at` field, so no API consumer can tell an archived issue from a live one — which is why the point above cannot be worked around client-side.
- LANGUAGE DRIFT: the assistant sometimes answers an English question in Russian (run mbu32v, `no-invented-identifier`: "Issue `9999` не найден в текущем рабочем пространстве." to "What is the status of issue 9999 in this workspace?"). The content was correct, only the language was not the caller's. The multilingual scenarios assert that a Russian/Uzbek/Chinese question is answered in kind; there is no scenario asserting the English direction, because the drift is not reliably reproducible. `no-invented-identifier` accepts denial phrasing in several languages so that it tests grounding rather than locale.
- TOOL RESULTS CAN BE LOST AFTER A WRITE: a run can end `failed` with "a write may have succeeded but its result could not be saved; review the affected item before retrying" (assistant/service.go, runToolCall returning false). `artifact-table-then-update` and `assign-to-self` hit it intermittently and are left as-is so the fix shows up on the scorecard.

## Data left behind

- User accounts (`agora-scn-*@agora.dev`) are never deleted — the API has no user-delete endpoint. They own nothing after teardown.
- Assistant sessions/messages/runs/artifacts are user-scoped, not workspace-scoped. The runner deletes the sessions it opened; a session whose run was still cancelling can survive the DELETE (409) and remain against the throwaway user.
- Everything else (workspaces, issues, projects, sprints, labels, comments, memberships, invitations) is removed by the cascading workspace delete.
