## 一句话概括其形态

Agora 是一个 **Go 后端**（Chi router、`sqlc` 生成的 DB 访问、用于实时通信的 `gorilla/websocket`），与 **PostgreSQL** 通信，前面是一个由共享无头逻辑的 TypeScript 应用组成的 **pnpm + Turborepo monorepo**，并由一个 **agent 守护进程** 供给工作——该守护进程轮询后端获取任务，并在本地运行编码智能体的 CLI。

## Go 后端形态

后端位于 `server/`。两个事实可以为一切定位：

- **router 是 Chi。** `server/cmd/server/router.go` 用 `chi.NewRouter()` 构建它，并挂载各个域的路由——守护进程端点位于 `r.Route("/api/daemon", …)` 下，webhook 位于顶层，工作区作用域的 API 位于鉴权中间件之后。
- **DB 访问由 `sqlc` 生成。** SQL 位于 `server/pkg/db/queries/`；`make sqlc` 在 `server/pkg/db/generated/` 中重新生成带类型的 Go 代码。Handler 和 service 调用 `Queries.*` 方法（例如 `Queries.GetAgent`、`Queries.CreateAgentTask`）——绝不手写 SQL。

**每个域一个 handler。** `server/internal/handler/` 每个关注点一个文件——`issue.go`、`comment.go`、`agent.go`、`daemon.go`、`chat.go`、`autopilot.go`、`project.go` 等等。Handler 在请求边界处解析并校验，然后把业务逻辑委托给 `server/internal/service/`。当一个 handler 为写查询解析 UUID 时，它必须遵守 `CLAUDE.md` 中的 **Backend Handler UUID Parsing Convention**（`parseUUIDOrBadRequest` / loader / `parseUUID`）——该约定的存在是因为一个静默的零值 UUID 曾让一个 `DELETE` 返回 204、却匹配了零行。

实时更新通过一个 hub 扇出：`server/cmd/server/main.go` 构造 `realtime.NewHub()`（工作区 WS 客户端）和一个独立的 `daemonws.NewHub()`（守护进程 WS 连接）。Service 广播协议事件（`protocol.EventTaskQueued`、`protocol.EventTaskRunning`、……），前端在收到时让其查询缓存失效——事件绝不直接写入客户端 store。

## task 生命周期

`server/internal/service/task.go` 在 `agent_task_queue` 表上拥有 agent-task 状态机。一个 task 经历 **enqueue → claim → start → complete/fail**（在任意时刻取消作为终止分支）。这是每一次智能体运行的脊柱。

<Mermaid chart={`
sequenceDiagram
  participant API as Backend (TaskService)
  participant PG as agent_task_queue
  participant D as Daemon
  API->>PG: CreateAgentTask (status=queued)
  API->>D: NotifyTaskEnqueued (WS wakeup)
  D->>API: POST /runtimes/{id}/tasks/claim
  API->>PG: ClaimAgentTask (queued→dispatched)
  API-->>D: task row
  D->>API: POST /tasks/{id}/start
  API->>PG: StartAgentTask (dispatched→running)
  D->>D: handleTask → executeAndDrain (agent runs)
  D->>API: POST /tasks/{id}/complete (or /fail)
  API->>PG: CompleteAgentTask (running→completed)
`} />

### Enqueue

多个入口创建一个 task，全部汇聚到一次 `Queries.Create*Task` 调用，随后是一次 WS 唤醒：

- `EnqueueTaskForIssue` —— 一个分配给智能体的 issue。不存储上下文快照；智能体在运行时通过 `agora` CLI 获取它需要的内容。
- `EnqueueTaskForMention` / `EnqueueTaskForSquadLeader` —— 一个在 comment 中被提及的智能体（squad-leader 变体打上 `is_leader_task=true` 标记）。
- `EnqueueChatTask` —— 一个聊天会话（没有 `issue_id`）。对于可产品化的拒绝场景，返回哨兵错误 `ErrChatTaskAgentArchived` / `ErrChatTaskAgentNoRuntime`。
- `EnqueueQuickCreateTask` —— 一个没有 issue/chat/autopilot 关联的自然语言提示词，作为 `QuickCreateContext` JSON 载荷（`Type: QuickCreateContextType`）存储。

每条路径都强制相同的前置条件（智能体未归档、`agent.RuntimeID` 已设置），广播 `protocol.EventTaskQueued`，然后调用 `NotifyTaskEnqueued`，这样守护进程会及时 claim，而不是等到下一次轮询 tick。顺序是有意为之的：**先**广播再 notify，因为 notify 路径会触发 dispatch 事件，而被重排的队列会让客户端在看到 "queued" 之前先看到 "dispatched"。

### Claim

守护进程轮询 `POST /api/daemon/runtimes/{runtimeId}/tasks/claim`，由 `ClaimTaskByRuntime` 处理，它调用 `TaskService.ClaimTaskForRuntime`。该方法：

1. 首先运行 `ReclaimStaleDispatchedTaskForRuntime`（恢复一个 claim 响应丢失的 task——参见 `claimResponseRecoveryWindow`，90s）。
2. 查询可选的 `EmptyClaimCache` 快速路径，以便在稳态空队列的情况下跳过一次 Postgres 扫描。
3. 列出 queued 候选项，并对每个不同的智能体调用 `ClaimTask(agentID)`。

`ClaimTask` 是原子化的核心：它对照 `agent.MaxConcurrentTasks` 检查 `CountRunningTasks`，运行 `ClaimAgentTask`（`queued → dispatched` 转换），对账智能体状态，并广播 `task:dispatch`。无容量或无 task 都返回 `(nil, nil)`——不是错误。

### Start、complete、fail

- `StartTask` 运行 `StartAgentTask`（`dispatched → running`）并广播 `protocol.EventTaskRunning`。**这里不改变 issue 状态**——由智能体通过 CLI 管理它。
- `CompleteTask` 在一个事务内运行 `CompleteAgentTask`（`running → completed`）。对于聊天 task，同一个事务会更新 `chat_session` 续接指针，关闭了一个竞态——否则下一条消息可能基于一个陈旧会话续接。它是**幂等的**：如果一个并行的智能体已经终结了该行，`WHERE status = 'running'` 不匹配任何内容，已存在的行作为成功被返回。
- 失败和取消复用相同的广播/对账形态；取消还会撤销为本次运行铸造的任何 `mat_` task token。

## agent SDK

`server/pkg/agent/` 是一个无头包——零守护进程、零 HTTP——它把每个编码智能体的 CLI 抽象到一个接口之后。

```go
type Backend interface {
    Execute(ctx context.Context, prompt string, opts ExecOptions) (*Session, error)
}
```

`Execute` 返回一个 `Session`，其 `Messages` 通道流式传输 `Message` 事件（`MessageText`、`MessageThinking`、`MessageToolUse`、`MessageToolResult`、`MessageStatus`、`MessageError`、`MessageLog`），其 `Result` 通道恰好投递一个最终的 `Result`。`Result.Status` 字段是本次运行处置结果的契约——取值为 `"completed"`、`"failed"`、`"aborted"`、`"timeout"`、`"cancelled"` 之一。

`agent.New(agentType, cfg)` 是一个对 **13 个后端** 的 switch：`claude`、`codebuddy`、`codex`、`copilot`、`opencode`、`openclaw`、`hermes`、`gemini`、`pi`、`cursor`、`kimi`、`kiro`、`antigravity`。未知类型会返回一个列出支持集合的错误。每个后端（`claude.go`、`codex.go`、……）把统一的 `ExecOptions`（`Cwd`、`Model`、`SystemPrompt`、`MaxTurns`、`Timeout`、`ResumeSessionID`、`ThinkingLevel`、`OpenclawMode`、`ExtraArgs`/`CustomArgs`、……）翻译成该 CLI 自己的 flag。并非每个后端都遵循每个选项——`ThinkingLevel`、`OpenclawMode` 和 `ExtraArgs` 精确记录了哪些后端会消费它们、哪些会静默忽略它们，这样支持可以增量增长，而不会破坏不相关的智能体。

`LaunchHeader(agentType)` 返回对用户可见的命令骨架（例如 `"claude (stream-json)"`），UI 把它作为用户 `custom_args` 将被追加到何处的预览展示。

## 守护进程：生产环境的调用方

`server/internal/daemon/daemon.go` 是把已 claim 的 task 变成运行中智能体的本地运行时。`Daemon.New` 接好 `runner = d.runTask`；`Daemon.Run` 完成启动序列——`resolveAuth`、`preflightAuth`（续期 PAT，然后初次工作区同步）、为每个工作区注册运行时、启动后台循环（`workspaceSyncLoop`、`taskWakeupLoop`、`heartbeatLoop`、`gcLoop`、`autoUpdateLoop`、`tokenRenewalLoop`）、把 `/health` 翻到 ready，然后进入 `pollLoop`。

当一个轮询器 claim 到一个 task 时，它交接给 `handleTask`，后者：

1. 如果 task 指向一个守护进程固定的 `project_resource`，获取 `local_directory` 路径锁（这样服务端状态是 `dispatched → waiting_local_directory → running`，绝不倒退）。
2. 把 env root 标记为 active，这样 GC 循环绝不回收一个存活的工作目录。
3. 启动 `watchTaskCancellation`，这样服务端的取消/删除会中断本次运行。
4. 调用 `d.runner.run` → `runTask`，它准备好环境并最终调用 **`executeAndDrain`**——真正驱动一个 `agent.Backend` 的函数。

`executeAndDrain(ctx, backend, prompt, opts, taskLog, taskID)` 是 agent SDK 的生产环境调用方。它：

- 调用 `backend.Execute`，然后排空 `session.Messages`，批处理 text/thinking 并把 tool-use/tool-result 事件通过 `ReportTaskMessages` 转发给服务端；
- 尽早固定智能体会话 id（`PinTaskSession`），这样守护进程在运行中途崩溃也能保留一个续接指针；
- 运行一个**空闲看门狗**来中断一个沉默的智能体，并在一个工具进行中时给予更大的预算（一个漫长的 `npm install` 不算卡死）；
- 返回最终的 `agent.Result` 加上一个工具计数。

`handleTask` 随后报告用量，并通过 `reportTaskResult` 路由结果，后者**失败时保守关闭**：只有 `result.Status == "completed"` 才调用 `d.client.CompleteTask`；其他每种状态——包括任何没人枚举过的未来状态——都走 `d.client.FailTask`，这样一个从未产生真实结果的运行绝不会被显示为 "Completed"。

## 前端依赖方向

monorepo 强制一个严格的、单向的依赖图。规则是：**`views → core + ui`**，其中 `core` 和 `ui` 彼此独立。

<Mermaid chart={`
flowchart TD
  app["apps/web · apps/desktop"] --> views["packages/views<br/>(shared business UI)"]
  views --> core["packages/core<br/>(headless logic + stores)"]
  views --> ui["packages/ui<br/>(atomic components)"]
  app --> core
  app --> ui
`} />

- `packages/core/` —— 无头业务逻辑和**所有** Zustand store。零 `react-dom`、零 `localStorage`、零 `next/*`、零 UI 库。
- `packages/ui/` —— 基于 shadcn 的原子组件。零 `@agora/core` import。
- `packages/views/` —— 共享的业务页面/组件。零 `next/*`、零 `react-router-dom`——路由通过 `NavigationAdapter`。

服务端状态与客户端状态以同等的严格性拆分：**TanStack Query** 拥有从 API 获取的一切（工作区作用域的查询以 `wsId` 为 key），**Zustand** 拥有客户端/UI 状态，而 **WS 事件让查询失效**，而不是写入 store。完整的理由和陷阱在 `CLAUDE.md` 中；本页只点明方向。

## 多租户

每个查询都按 `workspace_id` 过滤；成员检查把守访问；`X-Workspace-ID` header 把请求路由到正确的工作区。工作区作用域的前端查询以 `wsId` 为 key，这样切换工作区会自动替换缓存。

**Assignee 是多态的。** 一个 issue 携带 `assignee_type` + `assignee_id`（参见 `server/internal/handler/issue.go`），其中 `assignee_type` 是 `member`、`agent` 或 `squad` 之一。智能体路径（`assignee_type == "agent"`）正是让一个 issue 有资格进行 `EnqueueTaskForIssue` 的原因；squad 路径展开为该 squad 的多个智能体。正是这种多态，使得 task 生命周期通过 issue assignee 解析智能体，而不是假定是一个人类。
