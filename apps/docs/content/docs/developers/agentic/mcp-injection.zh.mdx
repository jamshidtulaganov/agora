## 那一个列

每个智能体携带一个 JSONB 列 `agent.mcp_config`。它在磁盘上的规范形态是 Claude 风格的：

```json
{
  "mcpServers": {
    "<name>": { "command": "...", "args": ["..."], "env": { "KEY": "..." } }
  }
}
```

某个服务器条目可以改为携带一个 `url`（外加可选的 `headers`）以表示一个远程 MCP 服务器，而不是一个 `command`。TypeScript 契约位于 `packages/core/mcp/types.ts`：

- `McpConfig` —— `{ mcpServers: Record<string, McpServerEntry> }`
- `McpServerEntry` —— `{ command: string; args?: string[]; env?: Record<string, string> }`
- `readMcpServers(config)` / `listMcpServers(config)` —— 防御性收窄读取；任何不是带有 `mcpServers` 映射的普通对象的值都会收窄为 `{}`（无服务器）。
- `upsertMcpServer` / `removeMcpServer` —— 管理 UI 使用的整对象读-改-写辅助函数。它们保留所有其他服务器：UI 从不局部修补单个键，而是读取整个对象，在 `mcpServers` 下设置/删除一个条目，再把整个对象写回。

守护进程在派发一个 task 时会把这个列原样复制到 `ExecOptions.McpConfig`（一个 `json.RawMessage`）中。从那里，`server/pkg/agent/` 中的每个后端将其具体化为底层 CLI 能理解的形式。

## 两个注入层

`mcp_config` 到达 CLI 有两种不同的方式，某个提供方使用哪一种取决于 CLI 是否能在启动时被告知 MCP，还是需要先把配置具体化到磁盘上。

<Mermaid chart={`

  COL["agent.mcp_config (JSONB)"] --> EXEC["ExecOptions.McpConfig (json.RawMessage)"]

  EXEC --> L2["Layer 2: server/internal/daemon/execenv preparers"]
  L1 --> CLAUDE["claude / codebuddy: --mcp-config file"]
  L1 --> CODEX["codex: CODEX_HOME/config.toml block"]
  L1 --> OPENCODE["opencode: OPENCODE_CONFIG_CONTENT env"]

`} />

**第 1 层 —— 智能体后端** 直接读取 `opts.McpConfig` 并在派生时塑造它。

**第 2 层 —— execenv 准备器** 在环境设置期间把 MCP 配置具体化到磁盘上，因为 CLI 是从 workdir/home 中的文件而不是从启动标志或环境变量发现 MCP 的。准备器接收相同的 `params.McpConfig`（见 `execenv.go`，其中 `McpConfig` 被转发进 `EnvParams` 并在环境复用时被重新使用）。

## 各提供方的机制

| 提供方 | 层 | 机制 | 源符号 |
|---|---|---|---|
| `claude` | backend | 把配置写入临时文件，追加 `--mcp-config <path>` + `--strict-mcp-config` | `claudeBackend.Execute`、`writeMcpConfigToTemp`、`buildClaudeArgs`（`claude.go`） |
| `codebuddy` | backend | 与 claude 相同 —— 临时文件 + `--mcp-config <path>` + `--strict-mcp-config` | `codebuddyBackend.Execute`、`buildCodebuddyArgs`（`codebuddy.go`） |
| `codex` | backend | 把一个 `[mcp_servers.*]` TOML 块渲染进 `$CODEX_HOME/config.toml` | `ensureCodexMcpConfig`、`renderCodexMcpServersBlock`（`codex.go`） |
| `opencode` | backend | 翻译为 OpenCode 的 `mcp` 切片，通过 `OPENCODE_CONFIG_CONTENT` 环境变量注入 | `buildOpenCodeMCPConfigContent`、`translateMCPConfigForOpenCode`（`opencode_mcp.go`） |
| `hermes` | backend | 翻译为 ACP 的 `session/new` `mcpServers` 数组 | `buildACPMcpServers`、`convertACPMcpServer`（`hermes.go`） |
| `kimi` | backend | 通过共享辅助函数的相同 ACP 数组 | `buildACPMcpServers`（在 `kimi.go` 中调用） |
| `kiro` | backend | 通过共享辅助函数的相同 ACP 数组 | `buildACPMcpServers`（在 `kiro.go` 中调用） |
| `cursor` | execenv | 写入 `.cursor/mcp.json` sidecar + `CURSOR_DATA_DIR` | `prepareCursorMcpConfig`（`execenv/cursor_mcp.go`） |
| `openclaw` | execenv | 重写 wrapper 配置的 `mcp` 块 | `execenv/openclaw_config.go` |

### claude / codebuddy

`claudeBackend.Execute` 通过 `writeMcpConfigToTemp`（用 `os.CreateTemp` 创建为 `agora-mcp-*.json`）把原始配置 JSON 写入一个临时文件，然后追加 `--mcp-config <path>`。一旦生命周期 goroutine 取得所有权，该临时文件就被删除。`buildClaudeArgs` 始终以 `--strict-mcp-config` 启动，因此守护进程写入的集合会替换 —— 而非合并 —— 任何全局 Claude MCP 配置。`codebuddy`（一个 Claude Code 分支）在 `buildCodebuddyArgs` 中是逐字节相同的模型。

在两个后端中，`--mcp-config` 都在 `blockedArgMode` 映射里（`claudeBlockedArgs` / `codebuddyBlockedArgs`，模式 `blockedWithValue`），所以用户提供的 `custom_args: ["--mcp-config", "..."]` 会被 `filterCustomArgs` 剥离并记录日志 —— 这个标志归守护进程所有。

### codex

`ensureCodexMcpConfig` 把一个以标记界定的块写入 `$CODEX_HOME/config.toml`：

```
# BEGIN agora-managed mcp_servers (do not edit; regenerated by daemon)
[mcp_servers.<name>]
command = "..."
# END agora-managed mcp_servers
```

标记是 `agoraCodexMcpBeginMarker` / `agoraCodexMcpEndMarker`。每次运行时都会先剥离先前的受管块（`codexMcpBlockRe`），以便重跑收敛。当存在受管配置时，`stripCodexUserMcpServerTables` 还会移除从 `~/.codex/config.toml` 继承的任何用户定义的 `[mcp_servers.*]` 表 —— 这是 codex 对 Claude 的 `--strict-mcp-config` 的等价物。它不能合并有两个原因：TOML 拒绝重新定义同一个表，并且一个保存了显式列表的管理员否则会看到全局服务器被悄悄并入。该文件被写入并 `chmod` 为 `0o600`，因为 `mcp_servers.<id>.env` 的值可能携带密钥，而 argv/`ps`/日志行不得携带。

`custom_args` 中用户的 `-c mcp_servers.…` / `--config mcp_servers.…` 覆盖会被 `filterCodexCustomConfigOverrides` 丢弃（codex 的 `-c` 是后者胜出，所以它们否则会重新遮蔽受管块）。键会被记录日志，值绝不会。

### opencode

`buildOpenCodeMCPConfigContent` 把配置翻译成 OpenCode schema 中仅 `mcp` 切片的部分，并通过 `OPENCODE_CONFIG_CONTENT` 环境变量注入（采用环境变量注入而非写入 `<workdir>/opencode.json`，这样该文件中智能体自己的模型/工具设置绝不会被覆盖）。`translateMCPConfigForOpenCode` 同时接受 Claude 风格的 `mcpServers` 和 OpenCode 原生的 `mcp` 形态，把 `command`+`args` 强制成一个数组、把 `env` 强制成 `environment`。每个条目 —— 包括翻译过的 —— 都会通过 `validateOpenCodeNativeMCPEntry` 重新校验，它用 `DisallowUnknownFields`（`strictDecode`）严格解码以强制 schema 的 `additionalProperties: false`。如果 `custom_env` 已经设置了 `OPENCODE_CONFIG_CONTENT`，则 `agent.mcp_config` 优先，并记录一条警告。

### hermes / kimi / kiro（ACP）

`buildACPMcpServers` 把 Claude 风格的对象-嵌-对象翻译成 ACP 的 `session/new` / `session/resume` 所期望的数组形态。`convertACPMcpServer` 对每个条目分类：一个 `command` 条目变成 stdio（`{name, command, args, env:[{name,value}]}`，无 `type`）；一个 `url` 条目变成 `{type, name, url, headers:[...]}`，`type` 默认为 `http`（接受 `sse`）。输出按确定性排序。在 `initialize` 握手之后，`filterACPMcpServersByCapability` 会丢弃那些其传输方式未在 `agentCapabilities.mcpCapabilities` 中由运行时声明的远程（`http`/`sse`）条目 —— 发送一个未声明的传输方式是一种 ACP 协议违规，会拒绝整个 `session/new`。

### cursor / openclaw（execenv）

`prepareCursorMcpConfig` 仅当智能体具有显式的受管配置（`hasManagedCursorMcpConfig`）时，才写入一个 Cursor 原生的 `.cursor/mcp.json` sidecar 并设置 `CURSOR_DATA_DIR`；一个 nil/null 的配置意味着"让 Cursor 正常运作"，不写入 sidecar。`openclaw_config.go` 从相同的受管配置检查出发，重写 openclaw wrapper 配置的 `mcp` 块。

## 严格模式契约

受管配置**替换**运行时的全局服务器；它从不与之求并集。每个提供方以自己的惯用法强制执行这一点：

- claude / codebuddy → `--strict-mcp-config`。
- codex → 当存在受管集合时，`stripCodexUserMcpServerTables` 移除继承来的 `[mcp_servers.*]` 表；`ensureCodexMcpConfig` 中的注释明确写道它"镜像 Claude 的 `--strict-mcp-config`"。
- opencode → `OPENCODE_CONFIG_CONTENT` 在 OpenCode 的 "local" 作用域合并，即最晚的合并位置，使守护进程条目优先于同键的用户条目。

产品规则：如果管理员在 MCP 标签页保存了一个显式列表，那么智能体看到的恰好就是那个列表 —— 全局/用户配置的服务器不会被悄悄加入。

## 三态语义

`mcp_config` 是一个真正的三态字段，在 API 边界处加以区分，而非折叠：

| 状态 | 线上值 | 含义 |
|---|---|---|
| 缺失 | SQL `NULL` / JSON `null` | CLI 默认 —— 回退到运行时自己的 MCP 设置 |
| 受管为空 | `{}` 或 `{"mcpServers":{}}` | 严格为空 —— 管理员保存了一个零服务器的受管集合；无全局回退 |
| 已填充 | `{"mcpServers":{...}}` | 严格 —— 恰好是这些服务器 |

`hasManagedCodexMcpConfig` 是规范的 Go 谓词：一个去空格后为空或字面 `null` 的值是**缺失**；其他一切（包括 `{}` 和 `{"mcpServers":{}}`）都是**存在**。对于 codex，"受管但为空"仍会写入 BEGIN/END 标记块，中间无表，把这个空意图固定在磁盘上并可供运维 grep。在 handler 一侧（`agent.go`），更新主体中的 `mcp_config: null` 会路由到 `ClearAgentMcpConfig`（把该列置为 NULL），而任何非 null 的值都被原样存储 —— `shouldClearMcpConfig` 把守这两条路径。

## 对畸形输入失败关闭

一个畸形的 `mcp_config` 会中止启动，而不是悄悄丢弃所有服务器并继承宿主的全局 MCP 设置 —— 那看起来会与"已保存的配置被应用"无法区分，而这恰恰是 MCP 标签页存在的意义所要消除的意外。

- codex → `ensureCodexMcpConfig` 返回一个错误，`codexBackend.Execute` 取消并返回 `apply codex mcp_config: …`。如果设置了受管配置但 `CODEX_HOME` 未设置，它也会失败。
- hermes / kimi / kiro → `buildACPMcpServers` 在顶层 JSON 畸形时返回一个错误，后端返回 `invalid mcp_config`。（既无 `command` 也无 `url` 的单个条目会被跳过并带一条警告，这样一个坏条目不会扼杀整个启动。）
- opencode → `validateOpenCodeNativeMCPEntry` 在配置到达 CLI 之前拒绝未知字段、错误的 `type`、缺失的 `command`/`url`、非正的 `timeout` 以及畸形的 `oauth`。

## 脱敏：智能体读不到自己的 mcp_config

MCP 服务器配置经常嵌入第三方 API 令牌。`redactMcpConfig`（`agent.go`）把响应上的 `mcp_config` 字段置空，并设置 `mcp_config_redacted: true`，以便 UI 能展示一个"已脱敏"的提示。这道关卡应用于 `ListAgents`、`GetAgent` 以及变更响应路径：

- **智能体行动者绝不会看到 `mcp_config`**，即使宿主的 PAT 能满足所有者/管理员角色关卡。这堵住了 MUL-2600 为 `custom_env` 堵住的同一条横向移动向量：一个在所有者守护进程下运行的智能体否则可以读取其他智能体的 MCP 密钥。
- 成员只有在 `canViewAgentSecrets` 通过且工作区的 `workspaceAlwaysRedactSecrets` 设置关闭时才能看到它。

守护进程仍然会把真正携带密钥的配置注入到派生的 CLI 中 —— 脱敏是读路径关注点，而非派发关注点。

## 待修复的漂移 bug：codebuddy 缺失于 MCP_SUPPORTED_PROVIDERS

`packages/core/agents/mcp-support.ts` 中的 `MCP_SUPPORTED_PROVIDERS` 是前端允许列表，它决定是否为某个提供方显示 MCP 配置标签页。它目前包含：

```
claude, codex, cursor, hermes, kimi, kiro, opencode, openclaw
```

但 `codebuddy` **遵循 `--mcp-config`** —— `codebuddyBackend.Execute` 写入临时文件并追加该标志，与 claude 完全一样，且 `codebuddyBlockedArgs` 为守护进程保留了 `--mcp-config`。因为 `codebuddy` 不在该集合中，`providerSupportsMcpConfig("codebuddy")` 返回 `false`，于是 codebuddy 智能体的 MCP 标签页被隐藏 —— 因此操作员无法配置后端本会乐于应用的 MCP 服务器。

**修复：** 把 `"codebuddy"` 加入 `MCP_SUPPORTED_PROVIDERS`。

<Callout type="warn" title="Same-PR sync rule">
`MCP_SUPPORTED_PROVIDERS` 与 `server/pkg/agent/` 中读取 `ExecOptions.McpConfig` 的后端集合（外加 `server/internal/daemon/execenv/` 中的 execenv 准备器）是**一个跨两种语言拆分的契约**。该文件自己的头部注释写道：保持此列表与读取 `ExecOptions.McpConfig` 的后端，以及那些其 execenv 准备器会具体化 MCP 配置的提供方同步。当你在 Go 中添加或移除某个提供方的 MCP 支持时，请在**同一个 PR** 中更新 `mcp-support.ts` —— 否则用户要么会保存一个运行时会忽略的值（提供方被过度列出），要么会被拒绝一个运行时本会遵循的标签页（提供方被少列出，即 codebuddy 的情况）。
</Callout>
