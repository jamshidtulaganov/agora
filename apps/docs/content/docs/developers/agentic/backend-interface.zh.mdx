`agent` 包（`server/pkg/agent/`）提供了一个接口——`Backend`——每个编码 agent 运行时（Claude Code、Codex、Copilot、OpenCode 等）都实现它。守护进程通过这个单一契约与它们全部对话，因此添加一个新 agent 仅意味着实现 `Backend.Execute`，别无其他。本页面以 `claude` 后端（`claude.go`）作为参考实现来描述这个契约，然后展示守护进程如何排空其结果。

## Backend 接口

```go
type Backend interface {
	// Execute runs a prompt and returns a Session for streaming results.
	Execute(ctx context.Context, prompt string, opts ExecOptions) (*Session, error)
}
```

`Execute` 有一个严格的时序契约，这是整个设计的核心：**快速返回一个非 nil 的 `*Session`，然后在 goroutine 中运行 CLI。** `Execute` 完成同步的、可能立即失败的工作——定位二进制文件、构建参数、启动子进程、连接管道——而一旦 `cmd.Start()` 成功，它就生成读取 stdout、写入 stdin 和等待退出的 goroutine，然后返回 `Session`。调用方绝不会在 `Execute` 内部阻塞等待 agent 完成；它转而等待 `Session` 的 channel。

返回的 `error` 意味着运行从未启动（找不到二进制文件、管道创建失败、`cmd.Start()` 失败）。在这种情况下 `*Session` 为 `nil`，没有任何东西需要排空。如果 `Execute` 返回一个非 nil 的 `*Session`，则 error 为 `nil`，调用方**必须**消费这些 channel。

## ExecOptions

`ExecOptions` 配置单次执行。后端只消费对其 CLI 有意义的字段；该后端无法识别的字段会被静默忽略而不是报错，因此可以在不破坏无关 agent 的情况下添加新选项。`claude` 后端读取的字段是：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `Cwd` | `string` | 子进程的工作目录（`cmd.Dir`） |
| `Model` | `string` | 非空时变为 `--model` |
| `SystemPrompt` | `string` | 非空时变为 `--append-system-prompt` |
| `MaxTurns` | `int` | `> 0` 时变为 `--max-turns` |
| `Timeout` | `time.Duration` | 挂钟时间上限；`<= 0` 意味着**无截止期限**（仅看门狗） |
| `ResumeSessionID` | `string` | 非空时变为 `--resume` |
| `ExtraArgs` | `[]string` | 守护进程级默认 CLI 参数，附加在 `CustomArgs` 之前 |
| `CustomArgs` | `[]string` | 每个 agent 的 CLI 参数，附加在 `ExtraArgs` 之后 |
| `McpConfig` | `json.RawMessage` | 非 nil 时，写入临时文件并通过 `--mcp-config` 传递 |
| `ThinkingLevel` | `string` | 非空时变为 `--effort`（空 = CLI 默认值） |

`Timeout` 值得强调。`agent.go` 中的 `runContext` 将其转化为子进程的 context：

```go
func runContext(ctx context.Context, timeout time.Duration) (context.Context, context.CancelFunc) {
	if timeout > 0 {
		return context.WithTimeout(ctx, timeout)
	}
	return context.WithCancel(ctx)
}
```

正的 `Timeout` 施加一个硬性的挂钟截止期限。零或负的 `Timeout` 施加**无**截止期限——存活性完全交给守护进程的非活动看门狗，因此一个持续发出事件的 session 绝不会仅仅因为运行时间长而被杀死（MUL-3064）。

## Session channel 协议

`Execute` 返回一个持有两个只读 channel 的 `Session`：

```go
type Session struct {
	// Messages streams events as the agent works. The channel is closed
	// when the agent finishes (before Result is sent).
	Messages <-chan Message
	// Result receives exactly one value — the final outcome — then closes.
	Result <-chan Result
}
```

生产 goroutine 必须遵守的协议是精确的，`claude.go` 是其规范实现：

1. `Messages` 是一个**容量为 256 的带缓冲 channel**（`make(chan Message, 256)`）。
2. `Result` 是一个**容量为 1 的带缓冲 channel**（`make(chan Result, 1)`）。
3. 随着 agent 工作，goroutine 在 `Messages` 上发送 `Message` 值。
4. 当 agent 完成时，goroutine **首先关闭 `Messages`**，然后在 `Result` 上发送**恰好一个** `Result`，再关闭 `Result`。

在 `claude.go` 中，顺序由工作 goroutine 中堆叠的 `defer` 强制保证。延迟函数以 LIFO 顺序执行，因此注册顺序

```go
defer cancel()
defer close(msgCh)
defer close(resCh)
```

意味着 `resCh` 最后被关闭。单个 `Result` 作为 goroutine 函数体的最后一条语句发送（`resCh <- Result{...}`），在扫描循环和 `cmd.Wait()` 完成之后——因此当 `Result` 被发送时，`Messages` 已经被延迟的 `close(msgCh)` 关闭了。由于 `Result` 容量为 1，即使还没有人在读取，该发送也绝不会阻塞。

### 为何采用这种精确形态

先关闭 `Messages` 再发 `Result` 的顺序让消费方可以将 channel 关闭用作其"agent 已完成流式输出"的信号，然后切换到等待 `Result` 以获取最终处置——而绝不会冒错过 `Result` 或死锁的风险。容量为 1 的 `Result` channel 保证生产方即使在消费方暂时繁忙时也能存入结果并退出；消费方随后再取走它。

## Message 与 MessageType

`Message` 是统一的流式事件。`MessageType` 是一个字符串类型的枚举，有七个值，全部在 `agent.go` 中声明为 Go 常量：

```go
const (
	MessageText       MessageType = "text"
	MessageThinking   MessageType = "thinking"
	MessageToolUse    MessageType = "tool-use"
	MessageToolResult MessageType = "tool-result"
	MessageStatus     MessageType = "status"
	MessageError      MessageType = "error"
	MessageLog        MessageType = "log"
)
```

`Message` 结构体携带一组字段；哪些字段被填充取决于 `Type`：

| 字段 | 为以下类型填充 |
| --- | --- |
| `Content` | `MessageText`、`MessageError`、`MessageLog` |
| `Tool` | `MessageToolUse`、`MessageToolResult` |
| `CallID` | `MessageToolUse`、`MessageToolResult` |
| `Input`（`map[string]any`） | `MessageToolUse` |
| `Output` | `MessageToolResult` |
| `Status` | `MessageStatus` |
| `Level` | `MessageLog` |
| `SessionID` | `MessageStatus`（早期 resume 指针固定） |

### 有界发送：trySend 丢弃，绝不阻塞

后端通过共享的 `trySend` 辅助函数在 `Messages` 上发送，绝不使用裸 channel 发送：

```go
func trySend(ch chan<- Message, msg Message) {
	select {
	case ch <- msg:
	default:
		// Channel full — drop message. Final output is accumulated
		// separately in Result.Output, so only streaming consumers are
		// affected.
	}
}
```

这是容量为 256 契约的另一半。缓冲区吸收突发，而当它满时，`trySend` **丢弃**该消息而不是阻塞 stdout 扫描器。被阻塞的扫描器会对 CLI 的 stdout 管道形成背压并使运行死锁。因此流式消费方在负载下可能错过中间消息——这是设计使然——但权威的最终文本会被单独累积到 `Result.Output` 中，所以当一条流式消息被丢弃时，没有任何面向用户的内容丢失。

## Result 与状态枚举

`Result` 是单一的最终结果：

```go
type Result struct {
	Status     string // "completed", "failed", "aborted", "timeout", "cancelled"
	Output     string // accumulated text output
	Error      string // error message if failed
	DurationMs int64
	SessionID  string
	Usage      map[string]TokenUsage // keyed by model name
}
```

`Status` 是一个**以字符串字面量表达的封闭枚举**——这些值故意没有 Go 常量。后端可设置的五个值是 `"completed"`、`"failed"`、`"aborted"`、`"timeout"` 和 `"cancelled"`。`claude` 后端在 `cmd.Wait()` 之后的尾部逻辑中分配它们：

| `Status` | `claude` 后端何时设置它 |
| --- | --- |
| `"completed"` | 默认；到达了一个无错误的 `result` 事件 |
| `"failed"` | CLI 报告了错误、在任何结果之前 prompt 写入失败、或进程以非零状态退出 |
| `"timeout"` | `runCtx.Err() == context.DeadlineExceeded`（`Timeout` 截止期限触发） |
| `"aborted"` | `runCtx.Err() == context.Canceled`（context 被取消，例如被空闲看门狗的 `agentCancel`） |
| `"cancelled"` | 由守护进程合成（见下文），而非由 `claude` 后端的退出分类器 |

<Callout type="warn">
由于 `Status` 是自由字符串，任何对其进行 switch 的消费方都必须有一个 `default` 分支。守护进程在下游又增加了两种处置——`"idle_watchdog"` 和 `"cancelled"`——没有任何后端会发出它们。即使后端只会写入这五个规范值，也要在消费方边界将该枚举视为开放的。
</Callout>

### TokenUsage 与 Result.Usage

token 计量是按模型进行的。`Result.Usage` 以模型名称为键，因此一次跨越多个模型的运行会分别报告每个模型的消耗：

```go
type TokenUsage struct {
	InputTokens      int64
	OutputTokens     int64
	CacheReadTokens  int64
	CacheWriteTokens int64
}
```

`claude` 后端在 `assistant` 消息到达时累积用量（汇总到 `usage` map 中对应模型的条目），并在存在时优先采用最终 `result` 事件中权威的 `modelUsage` 块（`claudeResultUsage`）。

## 守护进程如何消费这些 channel

`Daemon.executeAndDrain`（`server/internal/daemon/daemon.go`）是生产环境的消费方。它调用 `backend.Execute`，在向服务器转发事件的同时排空 `Session.Messages`，并等待 `Session.Result`——全部在空闲/工具看门狗之下进行。

骨架：

```go
agentCtx, agentCancel := context.WithCancel(ctx)
defer agentCancel()

session, err := backend.Execute(agentCtx, prompt, opts)
if err != nil {
	return agent.Result{}, 0, err
}
```

`executeAndDrain` 将调用方的 `ctx` 包装在 `agentCtx` 中，因此单次 `agentCancel()` 会同时中断**子进程**（看门狗取消交给 `Execute` 的 context）和排空循环。然后它：

1. **根据 `opts.Timeout` 设定排空截止期限。** 在 `Timeout` 为正时，排空 context 获得 `Timeout + 30s`（这个额外的窗口让它仍能在 stdout 卡住时收集后端自己的 `"timeout"` `Result`）。在 `Timeout <= 0` 时，排空 context **没有截止期限**——非活动看门狗是唯一的存活性保护网，与后端自己的无截止期限行为相匹配（MUL-3064）。
2. **启动空闲看门狗**（当 `AgentIdleWatchdog > 0` 时）通过 `runIdleWatchdog`。
3. **运行排空 goroutine**——一个对 `session.Messages`（以及 `drainCtx.Done()`）的 `for`/`select`，将 `text`/`thinking`/`tool_use`/`tool_result`/`error` 消息批处理，并每 500 毫秒通过 `d.client.ReportTaskMessages` 刷新到服务器。
4. **在外层 `select` 中等待 `session.Result`**。

排空循环在 `session.Messages` **被关闭**时退出（`case msg, ok := <-session.Messages: if !ok { goto drainDone }`）——正是后端协议承诺在发送 `Result` 之前进行的那次关闭。外层 select 随后接收单个 `Result`：

```go
select {
case result := <-session.Result:
	if idleWatchdogFired.Load() {
		result.Status = "idle_watchdog"
		...
	}
	return result, toolCount.Load(), nil
case <-drainCtx.Done():
	...
}
```

### 空闲/工具看门狗

`runIdleWatchdog` 是使无挂钟截止期限模式安全的机制。排空循环在每次有消息到达时盖上 `lastActivityAt`（unix 纳秒）。当后端沉默超过适用预算时，看门狗滴答并强制停止运行：

- **无工具在执行中** → 沉默超过 `AgentIdleWatchdog`（`window`）就是一次卡顿。
- **有工具在执行中**（一个 `tool_use` 还没有匹配的 `tool_result`，由 `inFlightTools` 计数器跟踪）→ 适用更大的 `AgentToolWatchdog`（`toolWindow`），因为一个真实的 `npm install` / `docker build` 合法地会沉默运行数分钟。`toolWindow <= 0` 完全禁用执行中边界。

在**两种**情况下，看门狗在触发前还要求 `len(session.Messages) == 0`——一条已缓冲但未排空的消息意味着是排空循环落后了，而非后端，因此它再等一个滴答。触发时，它记录是哪个阈值被越过，设置 `idleWatchdogFired`，并调用 `agentCancel()`。该取消传播进后端（后端将由此产生的 `context.Canceled` 翻译为 `Status: "aborted"`）；回到 `executeAndDrain` 中，`idleWatchdogFired` 检查将处置**重新打标**为 `"idle_watchdog"`，从而让 task 通过一个专用的失败原因被路由，而非进入通用的 aborted 桶。

`executeAndDrain` 还在 `drainCtx.Done()` 路径上合成仅属于守护进程的 `"cancelled"` 和 `"timeout"` 状态，区分上游取消（`context.Canceled` → `"cancelled"`）与真正的排空截止期限到期（`context.DeadlineExceeded` → `"timeout"`）。

## 强制性后端样板

每个监管子 CLI 的后端都必须连接相同的监管管道。跳过其中任何一项都会重新引入一个我们已经修复过的 bug。以 `claude.go` 为参考：

| 步骤 | 调用 | 为何是强制性的 |
| --- | --- | --- |
| 解析二进制文件 | `exec.LookPath(execPath)` | 当 CLI 缺失时快速失败（且从 `Execute` 中、在任何 goroutine 之前），返回一个 error + `nil` Session |
| 派生运行 context | `runContext(ctx, opts.Timeout)` | 正的 timeout → 硬截止期限；非正 → 仅看门狗（MUL-3064） |
| 构建子进程环境 | `cmd.Env = buildEnv(b.cfg.Env)` | 将 `os.Environ()` 与额外变量合并，并**剥离内部 Claude Code session 标记**（`isFilteredChildEnvKey`），使子进程不会将自己误认为嵌套/恢复的 session |
| 隐藏控制台窗口 | `hideAgentWindow(cmd)` | 防止 Windows 上闪烁的控制台窗口 |
| 限定强制杀死清理 | `cmd.WaitDelay = 10 * time.Second` | 在 context 取消后，给进程 10 秒退出，然后其 I/O 管道被强制关闭，因此 `cmd.Wait()` 不会在卡住的子进程上永久挂起 |
| 捕获有界 stderr | `newStderrTail(newLogWriter(...), agentStderrTailBytes)` 作为 `cmd.Stderr` | 保留 stderr 的最后 2048 字节，使 CLI 崩溃能浮现出真实原因，而非仅仅是 `exit status N` |
| 失败时附加尾部 | `withAgentStderr(finalError, "claude", stderrBuf.Tail())` | 将该尾部附加到 `Result.Error`，使失败无需翻查守护进程日志即可定位根因 |

### stderrTail 详解

`stderr_tail.go` 定义了一个线程安全的写入器，它将每个字节转发到守护进程日志**并**保留一个有界的尾部：

```go
const agentStderrTailBytes = 2048
```

`stderrTail.Write` 在互斥锁下追加到内部缓冲区，并从末尾将其裁剪回 `max` 字节，因此无论 CLI 写入多少，内存都保持有界。`Tail()` 返回去除首尾空白的内容；`withAgentStderr(msg, label, tail)` 组装最终的错误字符串（`msg + "; " + label + " stderr: " + tail`），在尾部为空时原样返回 `msg`。

`claude` 后端只在 `cmd.Wait()` 返回**之后**才采样 `stderrBuf.Tail()`——那时 `os/exec` 的 stderr 复制 goroutine 已观察到 CLI 写入的每个字节，所以尾部是完整的，且读取无竞态。

<Callout type="warn">
以上全部都是非可选的。环境剥离、`WaitDelay` 和 `stderrTail` 连接每一项都可追溯到一个具体的生产事故。当你添加一个新后端时，从 `claude.go` 复制监管形态，而非重新推导它。
</Callout>
