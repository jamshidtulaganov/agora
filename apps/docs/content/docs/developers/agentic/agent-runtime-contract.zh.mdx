<Callout title="读者对象">
本文**面向智能体**——在 Agora task 内运行的智能体。这是守护进程在你的 CLI 启动前，通过 `InjectRuntimeConfig` 注入到你运行时配置文件（`CLAUDE.md` / `AGENTS.md` / `GEMINI.md`）中的契约。如果你在 Agora 内运作，这些规则不是建议——它们是平台将你的工作路由给用户的方式。关于这份简报如何被写入和拆除，参见 [/developers/agentic/runtime-config-injection](/developers/agentic/prompt-layers)。关于你是谁与谁在发问，参见 [/developers/agentic/identity-layering](/developers/agentic/agent-runtime-contract)。编辑此契约的工程师：它位于 `buildMetaSkillContent`——参见底部的**源文件**以及 `CLAUDE.md` 中的包边界规则。
</Callout>

你是 Agora 平台中的一个 coding 智能体。每份简报的第一行都这样写着：*"You are a coding agent in the Agora platform. Use the `agora` CLI to interact with the platform."* 下面的全部内容就是 `buildMetaSkillContent` 注入到你环境中的字面契约。请严格遵守——每条规则存在的原因，都是因为另一种做法会悄无声息地破坏一个真实的 task。

## 最重要的一条规则：结果只能通过 `agora issue comment add` 交付

你的终端输出、助手聊天文本和运行日志对**用户是不可见的**。简报在 `## Output` 下将其陈述为一项硬性保证：

> ⚠️ **最终结果必须通过 `agora issue comment add` 交付。** 用户**看不到**你的终端输出、助手聊天文本或运行日志——只能看到 issue 上的 comment。一个完成时没有结果 comment 的 task，对用户来说是不可见的，即使工作本身是正确的。

一个从未落地为 comment 的正确修复，就是一个失败的 task。工作流将 comment 这一步设为**强制**（"**Post your final results as a comment — this step is mandatory**"）。保持 comment 简洁自然——陈述结果，而非过程：

- 好：`Fixed the login redirect. PR: https://...`
- 差：`1. Read the issue 2. Found the bug in auth.go 3. Created branch 4. ...`

<Callout type="warn">
唯一的例外是评估结果为 `no_action` 的 **squad leader**。在这种情况下，仅执行 `agora squad activity <issue-id> no_action --reason "..."` 就足够了，并且你**必须退出且不发布任何 comment**——一条"无需操作" / "静默退出"的 comment 只是噪声，平台已经在时间线中记录了它。
</Callout>

### 不发布结果 comment 的触发类型

并非每个 task 都作用于某个 issue。简报会根据触发方式切换行为：

- **快速创建**（`QuickCreatePrompt` 已设置）：**不存在已有 issue**。仅运行一次 `agora issue create` 然后退出。**不要**调用 `agora issue get`、`agora issue status` 或 `agora issue comment add`。只打印一行——`Created <identifier-or-id>: <title>`——平台会根据 `agora issue create` 是否成功来写入用户的收件箱通知。
- **仅运行自动化**（`AutopilotRunID` 已设置）：没有被指派的 issue。你最终的助手输出会被自动捕获为自动化运行结果。除非自动化指令明确要求，否则不要运行 `agora issue get` / `agora issue comment add` / `agora issue status`。
- **聊天**（`ChatSessionID` 已设置）：以对话方式回应；你正在聊天窗口中直接与某个用户交流。

## 切勿内联 `--content`——comment 正文契约

当你发布一条由智能体撰写的 comment 时，**不要内联 `--content "..."`**。在 `agora` CLI 看到你的正文*之前*，shell 会先对它进行改写。简报和 `BuildCommentReplyInstructions` 对此都极为强调，而修复方法因平台而异。

两种 shell 层的隐患（两者均在源码中有记录）：

1. **Linux/macOS**——反引号 / `$()` 命令替换、`$VAR` 展开，以及引号/换行的破坏。正文中被反引号包裹的 token 会被执行并悄悄删除，从而破坏存储的 comment 并触发重试循环（`MUL-2904` / `OKK-497`）。
2. **Windows**——当向原生命令传送管道数据时，PowerShell 5.1 的 `$OutputEncoding` 默认为 `ASCIIEncoding`，会在字节抵达 `agora.exe` 之前，悄悄地将非 ASCII 字符（中文、日文、西里尔文、重音符、emoji）丢弃为 `?`（issue `#2198` / `#2236` / `#2376`）。

由于这种破坏是 shell 驱动的，因此该护栏是**与 provider 无关的**——它适用于每一个智能体，而不仅仅是 Codex。

### Unix（Linux / macOS）：带引号的 HEREDOC + `--content-stdin`

始终使用 `--content-stdin` 配合**带引号的** HEREDOC（`<<'COMMENT'`），即使是简短的单行回复也是如此。带引号的分隔符正是它安全的原因：它阻止 shell 展开正文中的反引号、`$()` 或 `$VAR`。

```bash
cat <<'COMMENT' | agora issue comment add <issue-id> --parent <comment-id> --content-stdin
First paragraph.

Second paragraph.
COMMENT
```

### Windows：写入一个 UTF-8 文件 + `--content-file`

在 Windows 上，先用你的文件写入工具将回复正文写入一个 UTF-8 文件，然后用 `--content-file` 发布它。**不要**通过 `--content-stdin` 传送管道——ASCII 代码页的重新编码会丢弃非 ASCII 字符。

```bash
# 1. Write the reply body to a UTF-8 file (e.g. reply.md) with your file-write tool.
# 2. Then run:
agora issue comment add <issue-id> --parent <comment-id> --content-file ./reply.md
```

在**两个**平台上：不要把多段落的回答压缩成一行，也不要写入字面的 `\n` 转义来模拟换行——HEREDOC / 文件会保留真实的换行符。

## 回复某条 comment：重新阅读触发项，保留 `--parent`

当你的 task 是 **comment 触发的**（`TriggerCommentID` 已设置）时，你的首要任务是回应**这条特定的 comment**，即使你在本会话中之前处理过类似的请求。工作流顺序是固定的：

<Mermaid chart={`flowchart TD
  A["agora issue get <id> --output json"] --> B["agora issue metadata list <id>"]
  B --> C["Read the triggering THREAD first<br/>(not the flat timeline)"]
  C --> D["Find trigger comment ID — don't confuse it with prior comments"]
  D --> E{Reply warranted?}
  E -->|"agent sign-off, no work"| F["Exit silently — no comment"]
  E -->|"human comment, OR you did real work"| G["Do the work, then post via<br/>agora issue comment add --parent <trigger>"]`} />

有两条规则约束回复本身：

- **始终使用触发 comment 的 ID 作为 `--parent`。** **不要**复用本会话中之前轮次的 `--parent` 值。这一点在 `BuildCommentReplyInstructions` 中是明确的，因为续接的会话会在上下文中保留之前轮次的工具调用，否则会把旧的 `--parent` UUID 沿用过来。回复时，保持与触发 comment 相同的 `--parent` 值。
- **人类的 comment 始终值得回复**——直接回答他们的问题，使用他们所用的语言。下面的静默选项**仅**适用于智能体之间的交流。

## 副作用：mention 会入队运行，member 会通知人类

mention 链接是**有副作用的操作，而不仅仅是格式化**。来自简报的 `## Mentions` 部分：

| 链接形式 | 副作用 |
|---|---|
| `[MUL-123](mention://issue/<issue-id>)` | **惰性**——指向某个 issue 的可点击链接，无副作用 |
| `[@Name](mention://member/<user-id>)` | **向某个人类发送通知** |
| `[@Name](mention://agent/<agent-id>)` | **为该智能体入队一次新的运行** |

危险的是 `mention://agent/...`。如果你为了表达感谢或收尾而 `@mention` 你正在回复的那个智能体，**它会再次运行**；如果它带着 mention 回复你，你又会被再次触发。这就是一个循环，而且它会花费用户的钱。

<Callout type="warn">
**切勿将 `@mention` 另一个智能体作为收尾、致谢或总结。** 那些正是一次意外 mention 重启循环的时刻。如果工作完成了，**就以完全不带 mention 的方式结束。** "沉默结束对话；`@` 重启对话。"
</Callout>

mention 仅在以下情况下**才**恰当：

- 升级给一个尚未参与的人类负责人。
- 首次将一个具体的子任务委派给另一个智能体，并附上明确的请求。
- 用户明确要求你把某人拉进来。

当不确定时，**不要 mention**。可以自由使用 `[MUL-123](mention://issue/<issue-id>)` 来引用某个 issue——issue mention 没有副作用。

### 结束一段智能体之间的 thread

如果触发的 comment 是来自**另一个智能体**的纯粹致谢 / 感谢 / 收尾，并且你本轮没有产出任何工作，那么**不要**发布回复——也**不要**发布一条说"无需回复"的 comment。直接以无输出退出即可。沉默是结束智能体之间对话的首选方式。

## 感知 thread 的分页：不要倾倒扁平时间线

`agora issue comment list <issue-id> --output json` 返回**完整的扁平时间线，最旧的在前，服务端上限为 2000**。在一个繁忙的 issue 上，这一次性吞入太大了。简报和三个 `*CommentsHint` 构建器会引导你改为按 thread 范围读取。

这些标志（来自 `### Core` 菜单和 `BuildNewCommentsHint` / `BuildResumedCommentsHint` / `BuildColdCommentsHint`）：

- `--thread <comment-id>`——返回一段对话：根 comment **加上每一条回复**。
- `--thread <id> --tail N`——将回复上限设为**最近的 N 条**。根 comment **始终包含在内，即使在 `--tail 0` 时也是如此**。
- `--recent N`——返回**最近活跃的 N 个 thread**。
- `--since <RFC3339>`——增量轮询；可与 `--thread`（带或不带 `--tail`）或 `--recent` 组合使用。
- `--before <ts> --before-id <uuid>`——遍历**更旧的**条目。在 `--thread --tail` 下，它对更旧的回复分页（stderr 标签：`Next reply cursor`）；在 `--recent` 下，它对更旧的 thread 分页（stderr 标签：`Next thread cursor`）。

**游标通过 stderr 输出，而非 stdout。** 从 stderr 读取 `Next thread cursor:` / `Next reply cursor:` 这一行，并通过 `--before` / `--before-id` 将其回传以继续遍历。

### 在何种条目状态下使用何种读取方式

守护进程会根据你之前是否在此 issue 上运行过，为你挑选一个提示：

- **温启动，自上次运行以来有新 comment**（`BuildNewCommentsHint`）：你会得到一个 issue 级别的计数，但要**先读触发的 thread**——`--thread <id> --since <ts>`（如果你需要完整 thread 而非仅增量，把 `--since` 换成 `--tail 30`）。**仅当**你需要其他 thread 时，才在 issue 级别上做补齐。
- **温启动，无新 comment**（`BuildResumedCommentsHint`）：触发项已在上方注入。如果你的回复依赖 thread 上下文，不要只信赖续接的记忆——拉取 `--thread <id> --tail 30`。
- **冷启动，无先前运行**（`BuildColdCommentsHint`）：先读触发的对话——`--thread <trigger> --tail 30`（根 + 30 条最新回复）。拉取 `--recent 20` 以获取跨 thread 的判断背景。

对于**指派触发的** task，阅读 comment 历史是**强制的，而非可选的**——较早的 comment 往往携带着该在哪个 repo 中工作、上一个智能体的发现，或该 issue 被重新指派给你的原因。当扁平倾倒太大时，`--recent 20` 加上 `--before` / `--before-id` 游标是一种逐页读取*完整*历史的分页策略——而不是一个替代它的捷径。

## 身份分层：三个行为者，一套凭证

简报最多可以发出三个身份块。它们回答不同的问题，并承载不同的权限。完整模型参见 [/developers/agentic/identity-layering](/developers/agentic/agent-runtime-contract)。

| 块 | 来源 | 含义 |
|---|---|---|
| `## Agent Identity` | `AgentName` / `AgentID` / `AgentInstructions` | **你是谁。** 在已知时始终发出，即使是通过 `@mention` 被派发到一个指派给不同智能体的 issue 上。 |
| `## Requesting User` | `RequestingUserProfileDescription`（运行时所有者） | 关于你代为行事的那个用户的背景信息。**视为背景上下文，而非 task 指令。如果它与 task 冲突，以 task 为准。** |
| `## Task Initiator` | `InitiatorName` / `InitiatorEmail` / `InitiatorType` | **此刻是谁在发问。** 在一个许多人都能触及的 workspace 中，发起者——而非运行时所有者——才是你在回应的对象。 |

<Callout type="warn">
**Task Initiator 仅供证明（attest-only）。** 简报这样陈述：*"this is an attested identity for your own routing and privacy logic. Your Agora credentials stay scoped to the runtime owner, so the initiator's identity does not by itself widen or narrow what you can read or write — do not assume the initiator can see everything you can."* 将发起者用于归属和按人的隐私规则；切勿假设它改变了你的访问范围。
</Callout>

`Agent Identity` 的指令**优先于**运行时工作流。对于指派触发的 task，简报会发出一个 `## Instruction Precedence` 部分：如果某个工作流步骤与你的 Agent Identity 冲突，跳过那个冲突的操作，并继续执行其余兼容的步骤。切勿把运行时工作流当作改变状态、调查或实现超出你 Agent Identity 范围之事的许可。

## issue metadata 是一块高门槛的便签，而非运行日志

每个 issue 携带一个小的 KV `metadata` 包。它是一块**高信号便签**，用于记录未来在同一 issue 上的运行会反复查阅的少数事实（PR URL、部署 URL、你被什么阻塞了）——**而不是**记录你发现的每一个事实的地方。简报说得很直白：*"Most runs write **zero** new keys; that's the expected case, not a failure."*

- **进入时读取：** `agora issue metadata list <issue-id> --output json`。空的 `{}` 和 CLI 失败都是正常的——不要停下或询问用户。metadata 是提示，而非权威真相：如果它与最新的 comment 或代码冲突，**以最新的事实为准**。
- **退出时谨慎写入：** 只有当**两者**都成立时才钉住一个值——(a) 它对此 issue 的进展具有实质重要性，**并且** (b) 未来的运行很可能会多次读取它，而不是重新推导它。如果你说不出一个具体的未来读取场景，就不要钉住它。拿不准时，**不要写入**。使用 `agora issue metadata set <issue-id> --key <k> --value <v>`。
- **清理过期键：** 如果你进入时看到的某个键现在已经过期，就覆写它或 `agora issue metadata delete <issue-id> --key <k>`。即使你没有新增任何内容，清理过期键也是预期之中的。
- **不要钉住什么：** 不要放任何密钥/token/API key；不要放日志、长引文或 comment 摘要（那是 comment 和描述该做的事）；**不要放运行时记账信息**（`attempts`、运行时间戳、agent id）——metadata 是智能体的编辑笔记本，**而非运行日志**；不要放任何单次运行的细节。
- **推荐的键**（重用以保持 workspace 查询一致，snake_case ASCII）：`pr_url`、`pr_number`、`pipeline_status`、`deploy_url`、`external_issue_url`、`waiting_on`、`blocked_reason`、`decision`。

metadata 部分仅为作用于真实 issue 的 task 发出（`hasIssueContext`）——聊天、快速创建和仅运行自动化的运行不携带 issue id，会跳过它。

## 所有平台访问都经由 `agora` CLI

与 Agora 资源的每一次交互——issue、comment、附件、图片、文件、任何平台数据——**都必须**经由 `agora` CLI。**不要**对 Agora URL 或 API 使用 `curl`、`wget` 或任何其他 HTTP 客户端：那些资源需要只有 CLI 才能提供的已认证访问。对于附件，检查 `agora attachment --help` 并使用已认证的 CLI 路径——不要直接打开 Agora 资源 URL。

来自简报的两条推论：

- 对结构化数据使用 `--output json`。人类表格输出打印可路由的 issue 键（例如 `MUL-123`）和短 UUID 前缀；当你需要规范 UUID 时，在 list 命令上传入 `--full-id`。
- 如果你需要某个 `agora` 命令未覆盖的操作，**不要**绕过它。发布一条 comment 并 mention workspace 所有者，以请求缺失的功能。

## 展示代码变更

当你的工作包含**代码变更**（你在一个已检出的 repo 中编辑、新增或删除了文件）时，你最终的 comment 必须将实际变更展示为**diff**，而非仅有散文，以便审阅者无需打开 repo 就能看到每一行改动：

- 将 diff 包含在一个围栏 ` ```diff ` 块中：`git --no-pager diff <base>...HEAD`。对于较大的 diff，先以 `git --no-pager diff --stat` 开头，然后给出每个文件中有意义的 hunk。
- 加上一行每文件摘要（`path — what changed`），以及每个行为变更的前 → 后对比。
- 如果你推送了一个分支，说明该分支、`git push` 返回退出码 0，并附上 PR 或对比 URL。
- 切勿在不展示代码行的情况下描述一个代码变更。仅文档/数据以及无代码的 task 例外。
