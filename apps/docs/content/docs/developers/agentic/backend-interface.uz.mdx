`agent` paketi (`server/pkg/agent/`) bitta interfeysni — `Backend` ni — taqdim etadi, uni har bir coding-agent runtime'i (Claude Code, Codex, Copilot, OpenCode va boshqalar) amalga oshiradi. Daemon ularning barchasi bilan shu yagona kontrakt orqali gaplashadi, shu sababli yangi agent qoʻshish degani `Backend.Execute` ni amalga oshirish va boshqa hech narsa emas. Bu sahifa oʻsha kontraktni `claude` backend (`claude.go`) ni mos yozuvlar (reference) implementatsiyasi sifatida ishlatib tavsiflaydi, soʻngra daemon natijani qanday boʻshatishini koʻrsatadi.

## The Backend interface

```go
type Backend interface {
	// Execute runs a prompt and returns a Session for streaming results.
	Execute(ctx context.Context, prompt string, opts ExecOptions) (*Session, error)
}
```

`Execute` butun bu dizaynning yuragi boʻlgan qatʼiy vaqt kontraktiga ega: **nil boʻlmagan `*Session` bilan tez qayting, soʻngra CLI ni goroutine'larda ishlating.** `Execute` sinxron, darhol-muvaffaqiyatsiz-boʻlishi-mumkin boʻlgan ishni bajaradi — binarni topadi, argumentlarni quradi, subprocessni ishga tushiradi, pipe'larni ulaydi — va `cmd.Start()` muvaffaqiyatli boʻlgan onda stdout'ni oʻqiydigan, stdin'ga yozadigan va chiqishni kutadigan goroutine'larni ishga tushiradi, soʻngra `Session` ni qaytaradi. Chaqiruvchi hech qachon agent tugashini kutib `Execute` ichida bloklanib qolmaydi; uning oʻrniga `Session`ning kanallarini kutadi.

Qaytarilgan `error` run umuman boshlanmaganini bildiradi (binar topilmadi, pipe yaratish muvaffaqiyatsiz boʻldi, `cmd.Start()` muvaffaqiyatsiz boʻldi). Bunday holatda `*Session` `nil` boʻladi va boʻshatadigan (drain) hech narsa yoʻq. Agar `Execute` nil boʻlmagan `*Session` qaytarsa, error `nil` boʻladi va chaqiruvchi kanallarni **albatta** isteʼmol qilishi shart.

## ExecOptions

`ExecOptions` bitta bajarilishni konfiguratsiya qiladi. Backend'lar faqat oʻz CLI'siga maʼno beradigan maydonlarni isteʼmol qiladi; bu backendga notanish maydonlar xato bermasdan jimgina eʼtiborsiz qoldiriladi, shu sababli yangi opsiyalarni aloqasi boʻlmagan agentlarni buzmasdan qoʻshish mumkin. `claude` backend oʻqiydigan maydonlar:

| Field | Type | Maʼnosi |
| --- | --- | --- |
| `Cwd` | `string` | subprocess uchun ishchi katalog (`cmd.Dir`) |
| `Model` | `string` | boʻsh boʻlmaganda `--model` ga aylanadi |
| `SystemPrompt` | `string` | boʻsh boʻlmaganda `--append-system-prompt` ga aylanadi |
| `MaxTurns` | `int` | `> 0` boʻlganda `--max-turns` ga aylanadi |
| `Timeout` | `time.Duration` | wall-clock chegarasi; `<= 0` **deadline yoʻq** degani (faqat watchdog) |
| `ResumeSessionID` | `string` | boʻsh boʻlmaganda `--resume` ga aylanadi |
| `ExtraArgs` | `[]string` | daemon boʻyicha standart CLI argumentlar, `CustomArgs` dan oldin qoʻshiladi |
| `CustomArgs` | `[]string` | har bir agent uchun CLI argumentlar, `ExtraArgs` dan keyin qoʻshiladi |
| `McpConfig` | `json.RawMessage` | nil boʻlmaganda vaqtinchalik faylga yoziladi va `--mcp-config` orqali uzatiladi |
| `ThinkingLevel` | `string` | boʻsh boʻlmaganda `--effort` ga aylanadi (boʻsh = CLI standarti) |

`Timeout` alohida urgʻuga loyiq. `agent.go` dagi `runContext` uni subprocess kontekstiga aylantiradi:

```go
func runContext(ctx context.Context, timeout time.Duration) (context.Context, context.CancelFunc) {
	if timeout > 0 {
		return context.WithTimeout(ctx, timeout)
	}
	return context.WithCancel(ctx)
}
```

Musbat `Timeout` qatʼiy wall-clock deadline'ini joriy qiladi. Nol yoki manfiy `Timeout` **hech qanday** deadline joriy qilmaydi — tiriklik (liveness) butunlay daemonning faolsizlik watchdog'iga qoldiriladi, shunday qilib hodisalarni emit qilishda davom etadigan sessiya uzoq ishlagani uchungina oʻldirilmaydi (MUL-3064).

## The Session channel protocol

`Execute` ikkita faqat-qabul-qiluvchi kanalni ushlab turuvchi `Session` ni qaytaradi:

```go
type Session struct {
	// Messages streams events as the agent works. The channel is closed
	// when the agent finishes (before Result is sent).
	Messages <-chan Message
	// Result receives exactly one value — the final outcome — then closes.
	Result <-chan Result
}
```

Ishlab chiqaruvchi goroutine boʻysunishi shart boʻlgan protokol aniqdir va `claude.go` uning kanonik implementatsiyasidir:

1. `Messages` — sigʻimi **256 boʻlgan buferli kanal** (`make(chan Message, 256)`).
2. `Result` — sigʻimi **1 boʻlgan buferli kanal** (`make(chan Result, 1)`).
3. Agent ishlayotganda goroutine `Messages` ga `Message` qiymatlarini yuboradi.
4. Agent tugaganda goroutine **avval `Messages` ni yopadi**, soʻngra `Result` ga **aniq bitta** `Result` yuboradi, soʻngra `Result` ni yopadi.

`claude.go` da bu tartib worker goroutine'idagi ustma-ust qoʻyilgan `defer`'lar bilan taʼminlanadi. Kechiktirilgan funksiyalar LIFO tartibida bajariladi, shuning uchun roʻyxatga olish tartibi

```go
defer cancel()
defer close(msgCh)
defer close(resCh)
```

`resCh` eng oxirida yopilishini bildiradi. Yagona `Result` (`resCh <- Result{...}`) goroutine tanasining oxirgi operatori sifatida, scan sikli va `cmd.Wait()` tugagandan keyin yuboriladi — shu sababli `Result` yuborilgan vaqtga kelib `Messages` allaqachon kechiktirilgan `close(msgCh)` tomonidan yopilgan boʻladi. `Result` sigʻimi 1 boʻlgani uchun, hech kim hali oʻqimayotgan boʻlsa ham, bu yuborish hech qachon bloklanmaydi.

### Nega aynan shu shakl

Yopilgan `Messages`-soʻng-`Result` tartibi isteʼmolchiga kanal yopilishidan oʻzining "agent striming'ni tugatdi" signali sifatida foydalanish, soʻngra yakuniy natija (disposition) uchun `Result` ni kutishga oʻtish imkonini beradi — bunda hech qachon `Result` ni oʻtkazib yuborish yoki deadlock xavfi boʻlmaydi. Sigʻimi 1 boʻlgan `Result` kanali isteʼmolchi bir lahza band boʻlsa ham, ishlab chiqaruvchi natijani qoʻyib chiqib ketishi mumkinligini kafolatlaydi; isteʼmolchi uni keyinroq oladi.

## Message and MessageType

`Message` — birlashtirilgan striming hodisasi. `MessageType` — yetti qiymatli string-tipidagi enum boʻlib, hammasi `agent.go` da Go konstantalari sifatida eʼlon qilingan:

```go
const (
	MessageText       MessageType = "text"
	MessageThinking   MessageType = "thinking"
	MessageToolUse    MessageType = "tool-use"
	MessageToolResult MessageType = "tool-result"
	MessageStatus     MessageType = "status"
	MessageError      MessageType = "error"
	MessageLog        MessageType = "log"
)
```

`Message` struct'i bitta toʻplam maydonlarni olib yuradi; qaysi maydonlar toʻldirilishi `Type` ga bogʻliq:

| Field | Qaysisi uchun toʻldiriladi |
| --- | --- |
| `Content` | `MessageText`, `MessageError`, `MessageLog` |
| `Tool` | `MessageToolUse`, `MessageToolResult` |
| `CallID` | `MessageToolUse`, `MessageToolResult` |
| `Input` (`map[string]any`) | `MessageToolUse` |
| `Output` | `MessageToolResult` |
| `Status` | `MessageStatus` |
| `Level` | `MessageLog` |
| `SessionID` | `MessageStatus` (erta resume-pointer pinning) |

### Chegaralangan yuborish: trySend tashlab yuboradi, hech qachon bloklamaydi

Backend'lar `Messages` ga yalangʻoch kanal yuborishi bilan emas, balki umumiy `trySend` yordamchisi orqali yuboradi:

```go
func trySend(ch chan<- Message, msg Message) {
	select {
	case ch <- msg:
	default:
		// Channel full — drop message. Final output is accumulated
		// separately in Result.Output, so only streaming consumers are
		// affected.
	}
}
```

Bu cap-256 kontraktining ikkinchi yarmi. Bufer portlashlarni (burst) yutadi, va u toʻlganda `trySend` stdout skanerini bloklash oʻrniga xabarni **tashlab yuboradi**. Bloklangan skaner CLI'ning stdout pipe'iga teskari bosim (back-pressure) yaratardi va run'ni deadlock'ga olib kelardi. Shu sababli striming isteʼmolchilari yuk ostida oraliq xabarlarni oʻtkazib yuborishi mumkin — bu ataylab shunday qilingan — biroq vakolatli yakuniy matn alohida `Result.Output` ga toʻplanadi, shuning uchun striming xabari tashlab yuborilganda foydalanuvchiga koʻrinadigan hech narsa yoʻqolmaydi.

## Result and the status enum

`Result` — yagona yakuniy natija:

```go
type Result struct {
	Status     string // "completed", "failed", "aborted", "timeout", "cancelled"
	Output     string // accumulated text output
	Error      string // error message if failed
	DurationMs int64
	SessionID  string
	Usage      map[string]TokenUsage // keyed by model name
}
```

`Status` — **string literallari sifatida ifodalangan yopiq enum** — qiymatlar uchun ataylab hech qanday Go konstantalari yoʻq. Backend belgilashi mumkin boʻlgan besh qiymat: `"completed"`, `"failed"`, `"aborted"`, `"timeout"` va `"cancelled"`. `claude` backend ularni `cmd.Wait()` dan keyingi tail mantiqida belgilaydi:

| `Status` | `claude` backend uni qachon belgilaydi |
| --- | --- |
| `"completed"` | standart; xatosiz `result` hodisasi keldi |
| `"failed"` | CLI xato xabar berdi, natija kelmasdan oldin prompt yozish muvaffaqiyatsiz boʻldi yoki process nolga teng boʻlmagan kod bilan chiqdi |
| `"timeout"` | `runCtx.Err() == context.DeadlineExceeded` (`Timeout` deadline'i ishga tushdi) |
| `"aborted"` | `runCtx.Err() == context.Canceled` (kontekst bekor qilindi, masalan idle watchdog'ning `agentCancel` i tomonidan) |
| `"cancelled"` | daemon tomonidan sintez qilingan (quyiga qarang), `claude` backend'ning exit klassifikatori tomonidan emas |

<Callout type="warn">
`Status` erkin string boʻlgani uchun, unga `switch` qiladigan har qanday isteʼmolchida `default` shoxi boʻlishi shart. Daemon quyi oqimda yana ikkita natijani qoʻshadi — `"idle_watchdog"` va `"cancelled"` — ularni hech bir backend hech qachon emit qilmaydi. Backend'lar faqat besh kanonik qiymatni yozsalar ham, isteʼmolchi chegarasida enum'ni ochiq deb hisoblang.
</Callout>

### TokenUsage and Result.Usage

Token hisobi har bir model boʻyicha yuritiladi. `Result.Usage` model nomi boʻyicha kalitlanadi, shuning uchun bir nechta modelni qamragan bitta run har bir modelning isteʼmolini alohida hisobotda koʻrsatadi:

```go
type TokenUsage struct {
	InputTokens      int64
	OutputTokens     int64
	CacheReadTokens  int64
	CacheWriteTokens int64
}
```

`claude` backend `assistant` xabarlari kelishi bilan isteʼmolni toʻplaydi (`usage` map'idagi har-model yozuviga qoʻshib boradi) va mavjud boʻlganda yakuniy `result` hodisasidagi vakolatli `modelUsage` blokini afzal koʻradi (`claudeResultUsage`).

## How the daemon consumes the channels

`Daemon.executeAndDrain` (`server/internal/daemon/daemon.go`) — produksiyadagi isteʼmolchi. U `backend.Execute` ni chaqiradi, hodisalarni serverga uzatib turib `Session.Messages` ni boʻshatadi va `Session.Result` ni kutadi — barchasi idle/tool watchdog ostida.

Skelet:

```go
agentCtx, agentCancel := context.WithCancel(ctx)
defer agentCancel()

session, err := backend.Execute(agentCtx, prompt, opts)
if err != nil {
	return agent.Result{}, 0, err
}
```

`executeAndDrain` chaqiruvchining `ctx` sini `agentCtx` ga oʻraydi, shuning uchun yagona `agentCancel()` **ikkalasini ham** uzadi — subprocessni (watchdog `Execute` ga berilgan kontekstni bekor qiladi) va boʻshatish (drain) siklini. Soʻngra u:

1. **Boʻshatish deadline'ini `opts.Timeout` boʻyicha oʻlchaydi.** Musbat `Timeout` bilan drain kontekst `Timeout + 30s` oladi (qoʻshimcha oyna stdout tiqilib qolsa ham backend'ning oʻzining `"timeout"` `Result` ini hali ham toʻplash imkonini beradi). `Timeout <= 0` bilan drain kontekstda **deadline yoʻq** — faolsizlik watchdog'i yagona tiriklik toʻri, bu backend'ning oʻzining deadline'siz xatti-harakatiga mos keladi (MUL-3064).
2. **Idle watchdog'ni ishga tushiradi** (`AgentIdleWatchdog > 0` boʻlganda) `runIdleWatchdog` orqali.
3. **Boʻshatish goroutine'ini ishlatadi** — `session.Messages` (va `drainCtx.Done()`) boʻyicha `for`/`select`, `text`/`thinking`/`tool_use`/`tool_result`/`error` xabarlarini paketlab har 500 ms da `d.client.ReportTaskMessages` orqali serverga oqizadi.
4. **`session.Result` ni kutadi** tashqi `select` ichida.

Boʻshatish sikli `session.Messages` **yopilganda** chiqadi (`case msg, ok := <-session.Messages: if !ok { goto drainDone }`) — aynan backend protokoli `Result` ni yuborishdan oldin vaʼda qiladigan yopilish. Tashqi select keyin yagona `Result` ni qabul qiladi:

```go
select {
case result := <-session.Result:
	if idleWatchdogFired.Load() {
		result.Status = "idle_watchdog"
		...
	}
	return result, toolCount.Load(), nil
case <-drainCtx.Done():
	...
}
```

### The idle / tool watchdog

`runIdleWatchdog` — wall-clock-deadline'siz rejimni xavfsiz qiladigan narsa. Boʻshatish sikli xabar tushgan har safar `lastActivityAt` (unix nanosekundlar) ni shtamplaydi. Watchdog tiklaydi (tick) va backend tegishli byudjetdan tashqarida jim turganda run'ni majburan toʻxtatadi:

- **Hech qanday tool uchishda emas** → `AgentIdleWatchdog` (`window`) dan oshgan jimlik osilib qolish (hang) deb hisoblanadi.
- **Tool uchishda** (hali mos `tool_result` yoʻq `tool_use`, `inFlightTools` hisoblagichi orqali kuzatiladi) → kattaroq `AgentToolWatchdog` (`toolWindow`) qoʻllanadi, chunki haqiqiy `npm install` / `docker build` qonuniy ravishda daqiqalar davomida jimgina ishlaydi. `toolWindow <= 0` uchishdagi chegarani butunlay oʻchiradi.

**Ikkala** holatda ham watchdog ishga tushishdan oldin `len(session.Messages) == 0` boʻlishini ham talab qiladi — buferlangan-lekin-boʻshatilmagan xabar boʻshatish sikli orqada qolganini bildiradi, backend emas, shuning uchun u yana bir tick kutadi. Ishga tushganda u qaysi chegara oshib ketganini yozib oladi, `idleWatchdogFired` ni belgilaydi va `agentCancel()` ni chaqiradi. Bu bekor qilish backend'ga tarqaladi (u natijadagi `context.Canceled` ni `Status: "aborted"` ga aylantiradi); `executeAndDrain` ga qaytib, `idleWatchdogFired` tekshiruvi natijani `"idle_watchdog"` ga **qayta teglaydi**, shuning uchun task umumiy aborted bucket'i oʻrniga maxsus xatolik sababi orqali yoʻnaltiriladi.

`executeAndDrain` shuningdek `drainCtx.Done()` yoʻlida faqat-daemon'ga xos `"cancelled"` va `"timeout"` statuslarini sintez qiladi, yuqori oqimdagi bekor qilishni (`context.Canceled` → `"cancelled"`) haqiqiy drain-deadline tugashidan (`context.DeadlineExceeded` → `"timeout"`) farqlaydi.

## Mandatory backend boilerplate

Bola CLI'sini nazorat qiladigan har bir backend bir xil nazorat (supervisory) infratuzilmasini ulashi shart. Uning birortasini oʻtkazib yuborish biz allaqachon tuzatgan bug'ni qayta kiritadi. `claude.go` ni mos yozuv sifatida ishlatib:

| Step | Call | Nega majburiy |
| --- | --- | --- |
| Binarni aniqlash | `exec.LookPath(execPath)` | CLI yoʻq boʻlganda tez muvaffaqiyatsiz boʻlish (va `Execute` dan, har qanday goroutine'dan oldin), error + `nil` Session qaytarish |
| Run kontekstini olish | `runContext(ctx, opts.Timeout)` | musbat timeout → qatʼiy deadline; nomusbat → faqat-watchdog (MUL-3064) |
| Bola env'ini qurish | `cmd.Env = buildEnv(b.cfg.Env)` | `os.Environ()` ni qoʻshimcha oʻzgaruvchilar bilan birlashtiradi va **ichki Claude Code sessiya markerlarini olib tashlaydi** (`isFilteredChildEnvKey`), shunda bola oʻzini ichki-joylashgan/qayta-tiklangan sessiya deb adashtirmaydi |
| Konsol oynasini yashirish | `hideAgentWindow(cmd)` | Windows'da chaqnab turuvchi konsol oynasining oldini oladi |
| Majburiy-kill tozalashni chegaralash | `cmd.WaitDelay = 10 * time.Second` | kontekst bekor qilingandan keyin, I/O pipe'lari majburan yopilishidan oldin processga chiqish uchun 10 s beradi, shunda `cmd.Wait()` tiqilib qolgan bola ustida abadiy osilib qolmaydi |
| Chegaralangan stderr'ni ushlash | `newStderrTail(newLogWriter(...), agentStderrTailBytes)` `cmd.Stderr` sifatida | stderr'ning oxirgi 2048 baytini saqlaydi, shunda CLI qulashi shunchaki `exit status N` oʻrniga haqiqiy sababni yuzaga chiqaradi |
| Muvaffaqiyatsizlikda tail'ni biriktirish | `withAgentStderr(finalError, "claude", stderrBuf.Tail())` | oʻsha tail'ni `Result.Error` ga qoʻshadi, shunda muvaffaqiyatsizliklar daemon log'larini titmasdan ildiz-sababi aniqlanadigan boʻladi |

### stderrTail batafsil

`stderr_tail.go` har bir baytni daemon log'iga uzatadigan **va** chegaralangan tail'ni saqlaydigan thread-safe yozuvchini aniqlaydi:

```go
const agentStderrTailBytes = 2048
```

`stderrTail.Write` mutex ostida ichki buferga qoʻshadi va uni oxiridan `max` baytgacha qisqartirib qaytaradi, shunda CLI qancha yozsa ham xotira chegaralangan boʻlib qoladi. `Tail()` boʻshliqlari kesilgan kontentni qaytaradi; `withAgentStderr(msg, label, tail)` yakuniy error string'ini quradi (`msg + "; " + label + " stderr: " + tail`), tail boʻsh boʻlganda `msg` ni oʻzgartirmasdan qaytaradi.

`claude` backend `stderrBuf.Tail()` ni faqat `cmd.Wait()` qaytgandan **keyin** sample qiladi — oʻsha nuqtada `os/exec`ning stderr nusxa goroutine'i CLI yozgan har bir baytni koʻrgan boʻladi, shuning uchun tail toʻliq va oʻqish race'siz boʻladi.

<Callout type="warn">
Yuqoridagilarning barchasi ixtiyoriy emas. env-strip qilish, `WaitDelay` va `stderrTail` ulanishlarining har biri aniq produksiya hodisasiga taqaladi. Yangi backend qoʻshganingizda, nazorat shaklini qaytadan keltirib chiqarish oʻrniga `claude.go` dan nusxa oling.
</Callout>
