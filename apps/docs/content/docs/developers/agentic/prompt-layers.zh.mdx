受众：**两类** —— 编辑守护进程提示词代码的后端工程师，以及在推理任务为何以这种方式被描述给自己的智能体。如果你正在添加一种新的任务类别、修改某个让智能体运行的 CLI 标志，或者疑惑为何回复规则会出现在两个地方，这就是你需要的页面。另请参阅 [/developers/agentic/task-kinds](/developers/agentic/prompt-layers)、[/developers/agentic/runtime-config](/developers/agentic/prompt-layers) 和 [/developers/conventions](/developers/conventions)。

当守护进程把任务分派给某个编码智能体 CLI 时，它通过**两个分层**来描述该任务，这两层由两个不同文件中的两个不同函数写入。把这个划分做对，正是让每轮消息保持低成本、让常驻指令保持稳定的关键。

- **第 1 层 —— 易变的每轮消息。** `server/internal/daemon/prompt.go` 中的 `BuildPrompt` 返回一个简短字符串，作为用户回合交给智能体。它每轮都会变化：这条 comment、这个触发 ID、这条聊天消息。
- **第 2 层 —— 稳定的运行时配置骨架。** `server/internal/daemon/execenv/runtime_config.go` 中的 `buildMetaSkillContent` 返回一份较长的 markdown 简报，由 `InjectRuntimeConfig` 写入提供方的原生配置文件（`CLAUDE.md` / `AGENTS.md` / `GEMINI.md`）。它是智能体在整个运行期间的常驻操作手册。

## 划分：易变 vs 稳定

这两层的存在是为了让每个事实恰好只存活在一个地方，以其变化频率为依据。

| | 第 1 层 —— `BuildPrompt` | 第 2 层 —— `buildMetaSkillContent` |
|---|---|---|
| 文件 | `server/internal/daemon/prompt.go` | `server/internal/daemon/execenv/runtime_config.go` |
| 输出 | 每轮消息字符串 | markdown 简报 |
| 写入到 | 智能体的用户回合 | `CLAUDE.md` / `AGENTS.md` / `GEMINI.md` |
| 生命周期 | **易变** —— 每轮重建 | **稳定** —— 运行期间的常驻骨架 |
| 承载 | 这条 comment 正文、这个触发 ID、这条聊天消息、这条 quick-create 输入 | 身份、工作区上下文、可用命令、工作流、mentions/attachments 规则 |

规则是：**每轮变化的事实属于第 1 层；在整个运行期间保持不变的事实属于第 2 层。** 触发的 comment 正文是易变的，因此 `buildCommentPrompt` 将其直接嵌入（`> %s`），这样智能体"即使在复用的 workdir 中存在过期输出文件时也不会错过它"。`agora` CLI 命令列表是稳定的，因此它只在 `buildMetaSkillContent` 的 `## Available Commands` 下出现一次，而不是每轮都重新发出。

## 第 1 层：`BuildPrompt` 与五个任务类别分支

`BuildPrompt(task Task, provider string) string` 是一个轻量分派器。它检查任务并按照这个确切顺序路由到五个构建器之一：

1. `task.ChatSessionID != ""` → `buildChatPrompt(task)`
2. `task.TriggerCommentID != ""` → `buildCommentPrompt(task, provider)`
3. `task.AutopilotRunID != ""` → `buildAutopilotPrompt(task)`
4. `task.QuickCreatePrompt != ""` → `buildQuickCreatePrompt(task)`
5. 否则 → 内联的 **assignment** 分支（无辅助函数；`BuildPrompt` 直接构建它）

`BuildPrompt` 上的文档注释陈述了整个分层的契约：*"Keep this minimal — detailed instructions live in CLAUDE.md / AGENTS.md injected by `execenv.InjectRuntimeConfig`."* 每个分支只发出对该类别而言易变的内容：

- **chat**（`buildChatPrompt`）—— 发出 `task.ChatMessage`、任何显式选择的 `/`-skills，以及每条消息的 `task.ChatMessageAttachments`（按 `id`/`filename` 列出，以便智能体通过 `agora attachment download <id>` 获取它们，而不是一个过期的 CDN URL）。
- **comment**（`buildCommentPrompt`）—— 将 `task.TriggerCommentContent` 嵌入为引用块、一个作者标签，以及针对*这个*触发的 comment 阅读 + 回复指令。`provider` 仅因为回复模板是平台感知的而被传入。
- **autopilot**（`buildAutopilotPrompt`）—— 发出仅运行期自动化的 ID、标题、来源、触发载荷和描述。明确以 `Do not run agora issue get; this run does not have an issue ID.` 结尾。
- **quick-create**（`buildQuickCreatePrompt`）—— 发出用户的 `task.QuickCreatePrompt` 以及完整的字段/输出规则（见下方的例外）。
- **assignment**（兜底分支）—— 所有分支中最轻量的：`Your assigned issue ID is: %s` 加上指向 `agora issue get %s --output json` 的指针以及 comment 历史规则。详细的分步工作流完全存活在第 2 层中。

## 第 2 层：`buildMetaSkillContent` 与运行时配置文件

`InjectRuntimeConfig(workDir, provider string, ctx TaskContextForEnv)` 调用 `buildMetaSkillContent(provider, ctx)`，并通过 `runtimeConfigPath` 把结果写入提供方的原生配置文件：

- `claude`、`codebuddy` → `CLAUDE.md`
- `codex`、`copilot`、`opencode`、`openclaw`、`hermes`、`pi`、`cursor`、`kimi`、`kiro`、`antigravity` → `AGENTS.md`
- `gemini` → `GEMINI.md`
- 未知提供方 → `""`（仅提示词模式，不写入文件）

这份简报是一份厚重、基本静态的 markdown 文档。它以 `# Agora Agent Runtime` 开头，然后从 `ctx` 组装各个章节：`## Agent Identity`、`## Requesting User`、`## Task Initiator`、`## Workspace Context`、`## Available Commands`、`## Comment Formatting`、`## Showing Code Changes`、`## Repositories`、`## Project Context`、`## Issue Metadata`、一个 `### Workflow` 块、`## Mentions`、`## Attachments` 以及 `## Output`。`### Workflow` 块本身按任务类别分支（chat / quick-create / autopilot / comment / assignment）—— 但承载的是**常驻**指令，而非本轮数据。

`InjectRuntimeConfig` 不会覆盖用户自己的配置。它用标记注释（`runtimeMarkerBegin` / `runtimeMarkerEnd`）包裹简报，`writeRuntimeConfigFile` 要么创建文件，要么在固定的 `runtimeManagedSeparator` 之后追加，要么就地替换已有的块。`CleanupRuntimeConfig` 会逐字节地精确逆转这一操作 —— 这对 `local_directory` 流程很重要，因为那里的 `WorkDir` 是用户自己的仓库。

## 为何这个划分不可妥协：单一事实来源

这个划分的要点是**每个事实只有一个写入者**。易变事实恰好有一个写入者（`BuildPrompt`）；稳定事实恰好有一个写入者（`buildMetaSkillContent`）。当同一条指令必须出现在*两个*界面时，它由**一个从两侧调用的共享构建器**生成 —— 绝不内联两次。

这是反漂移规则，`server/internal/daemon/execenv/reply_instructions.go` 就是它被强制执行的地方。四个构建器存活在那里，每个都从第 1 层和第 2 层同时调用：

- `BuildNewCommentsHint(issueID, triggerCommentID, triggerThreadID, newCommentsSince string, newCommentCount int)`
- `BuildResumedCommentsHint(issueID, triggerCommentID, triggerThreadID string)`
- `BuildColdCommentsHint(issueID, triggerCommentID, triggerThreadID string)`
- `BuildCommentReplyInstructions(provider, issueID, triggerCommentID string)`

例如，`buildCommentPrompt`（第 1 层）以 `b.WriteString(execenv.BuildCommentReplyInstructions(provider, task.IssueID, task.TriggerCommentID))` 结尾，而 `buildMetaSkillContent`（第 2 层）的 comment 分支在第 7 步调用完全相同的 `BuildCommentReplyInstructions(provider, ctx.IssueID, ctx.TriggerCommentID)`。两个界面发出相同的回复模板 —— 在 Linux/macOS 上为带引号的 HEREDOC，在 Windows 上为 `--content-file` —— 以及相同的 comment 阅读提示。构建器的文档注释明确陈述了这个要求：*"Both surfaces call this so the cold fallback cannot drift between them"* 以及 *"Both the per-turn prompt (`daemon.buildCommentPrompt`) and the CLAUDE.md workflow (`InjectRuntimeConfig`) call this so the two surfaces cannot drift (hard requirement from PR #2816)."*

<Callout title="The rule">
如果一个句子必须同时出现在每轮消息和运行时简报中，请在 `reply_instructions.go` 的某个构建器中写一次，然后从 `prompt.go` 和 `runtime_config.go` 同时调用该构建器。绝不要把文本复制粘贴到两处 —— 副本会漂移，智能体会得到相互矛盾的指令（一个过期的 `--parent` UUID 就是经典的失败案例）。
</Callout>

## quick-create 的例外

quick-create 故意打破了"详细规则存活在第 2 层"的模式。完整的字段规则（title、description、priority、assignee、project、parent、status、attachments）以及严格的输出契约（`Run exactly one agora issue create --output json invocation`）存活在**第 1 层** —— `buildQuickCreatePrompt` —— 中，而非简报中。

原因在 `buildMetaSkillContent` 的 quick-create `### Workflow` 分支的代码注释里：quick-create 是**一次性**的，因此每轮消息总是存在，从而在那里给了它一个单一事实来源。第 2 层只保留硬性护栏，这样即便某个提供方没有把用户消息传播进其工作上下文（或在恢复的会话中），也仍能避免对一个空的 issue ID 运行 assignment 工作流：

```text
**This task was triggered by quick-create.** There is NO existing Agora issue.
Follow the field and output rules in the user message you just received; ignore
the default assignment-task workflow.
```

因此正常的划分（易变在第 1 层，稳定在第 2 层）在这里发生了反转：详细规则是邻近易变的（它们描述如何处理*这一个*输入），而一次性的本质保证了每轮消息总是会被读取。

## `TaskContextForEnv`：共享的易变结构体

两层都从任务上下文读取。第 2 层读取 `TaskContextForEnv`（定义在 `server/internal/daemon/execenv/execenv.go`）；第 1 层读取守护进程的 `Task`。区分任务类别的字段在两侧是同一组：`ChatSessionID`、`TriggerCommentID`、`AutopilotRunID`、`QuickCreatePrompt`，以及 `IssueID`。

这就是为什么**一种新的任务类别会同时触及两层**。要添加一种，你必须：

1. 向 `Task` 和 `TaskContextForEnv` 添加一个判别字段。
2. 向 `BuildPrompt`（第 1 层）添加一个分支，用于易变的每轮消息。
3. 向 `buildMetaSkillContent`（第 2 层）的 `### Workflow` 块添加一个分支，并更新 `hasIssueContext` / `isAssignmentTriggered` 护卫，使新类别不会意外落入以 issue 为中心的路径。

跳过第 2 步或第 3 步会产生一个半接通的类别：正确的每轮消息搭配错误的常驻工作流，或反之。现有的护卫使这一点具体化 —— `hasIssueContext := ctx.ChatSessionID == "" && ctx.QuickCreatePrompt == "" && ctx.AutopilotRunID == ""` 和 `isAssignmentTriggered := ... && ctx.TriggerCommentID == ""` 都枚举了每一种非 assignment 类别，因此未被添加进它们的新类别会被错误分类。

## squad-leader 检测在各层中有所不同

squad-leader 行为（智能体可以静默退出并记录 `agora squad activity <issue-id> no_action`，而非发布一条 comment）在每层中以不同方式被门控，而这个差异值得了解：

- **第 2 层** 读取 `TaskContextForEnv` 上预先计算的布尔值 `ctx.IsSquadLeader`（注释为 *"true when the agent is acting as a squad leader (may exit silently on no_action)"*）。`### Workflow` 和 `## Output` 章节基于它分支。
- **第 1 层**，在 `buildCommentPrompt` 中，通过**对协议字符串做子串匹配**来内联检测它：`task.Agent != nil && strings.Contains(task.Agent.Instructions, "## Squad Operating Protocol")`。当该子串存在时，它会把 squad-leader 的 `no_action` 规则发出到每轮消息中。

因此 squad-leader 契约有两个触发器：第 2 层中的一个结构体布尔值，以及第 1 层中针对智能体指令的一次字面字符串匹配。如果你重命名 `## Squad Operating Protocol` 标题，第 1 层的检测会静默地停止触发 —— 把那个字符串视为一个契约。

## 提示词缓存的影响（简述）

稳定优先的排序也是一种缓存优化。因为较长的 `buildMetaSkillContent` 简报在各轮之间保持稳定，而发生变化的是较短的 `BuildPrompt` 消息，那些对提示词做前缀缓存的提供方会在庞大稳定的骨架上获得缓存命中，每轮只需为处理那一小段易变尾部付费。把易变内容排除在简报之外 —— 并且在顺序上排在稳定内容之后 —— 正是保全那道缓存边界的做法。这是划分的一个结果，而非其主要动机；主要动机是单一事实来源。
