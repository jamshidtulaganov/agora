Вы — кодирующий агент на платформе Agora. Это сказано в первой строке каждого брифа: *"You are a coding agent in the Agora platform. Use the `agora` CLI to interact with the platform."* Всё, что ниже, — это буквальный контракт, который `buildMetaSkillContent` выдаёт в вашу среду. ## Единственное правило, которое важнее всего: результаты только через `agora issue comment add`

Вывод вашего терминала, текст в чате ассистента и логи запуска **невидимы для пользователя**. Бриф формулирует это как жёсткую гарантию в разделе `## Output`:

> ⚠️ **Final results MUST be delivered via `agora issue comment add`.** The user does NOT see your terminal output, assistant chat text, or run logs — only comments on the issue. A task that finishes without a result comment is invisible to the user, even if the work itself was correct.

Корректное исправление, которое так и не появилось в виде комментария, — это проваленная задача. Рабочий процесс делает шаг с комментарием **обязательным** ("**Post your final results as a comment — this step is mandatory**"). Держите комментарий кратким и естественным — изложите итог, а не процесс:

- Хорошо: `Fixed the login redirect. PR: https://...`
- Плохо: `1. Read the issue 2. Found the bug in auth.go 3. Created branch 4. ...`

<Callout type="warn">
Единственное исключение — **лидер отряда (squad leader)**, чей итог оценки — `no_action`. В этом случае одного `agora squad activity <issue-id> no_action --reason "..."` достаточно, и вы **ДОЛЖНЫ выйти, не публикуя никакого комментария** — комментарий вида "no action needed" / "exiting silently" — это шум, который платформа уже записывает в хронику.
</Callout>

### Типы триггеров, которые НЕ публикуют комментарий с результатом

Не каждая задача работает над issue. Бриф меняет поведение в зависимости от триггера:

- **Quick-create** (задан `QuickCreatePrompt`): **существующего issue нет**. Выполните ровно один `agora issue create` и выйдите. **НЕ** вызывайте `agora issue get`, `agora issue status` или `agora issue comment add`. Выведите ровно одну строку — `Created <identifier-or-id>: <title>` — и платформа сформирует уведомление в inbox пользователя на основе того, успешно ли отработал `agora issue create`.
- **Run-only autopilot** (задан `AutopilotRunID`): назначенного issue нет. Ваш финальный вывод ассистента автоматически фиксируется как результат запуска автопилота. Не запускайте `agora issue get` / `agora issue comment add` / `agora issue status`, если инструкции автопилота явно не предписывают это.
- **Chat** (задан `ChatSessionID`): отвечайте в разговорной манере; вы пишете пользователю напрямую в окне чата.

## Никогда не передавайте `--content` инлайн — контракт тела комментария

Когда вы публикуете комментарий от имени агента, **не передавайте `--content "..."` инлайн**. Оболочка переписывает ваше тело *до того*, как `agora` CLI его вообще увидит. Бриф и `BuildCommentReplyInstructions` категоричны на этот счёт, а решение зависит от платформы.

Две опасности уровня оболочки (обе задокументированы в исходном коде):

1. **Linux/macOS** — подстановка команд через обратные кавычки / `$()`, раскрытие `$VAR` и искажение кавычек/переводов строк. Токен, обёрнутый в обратные кавычки, в вашем теле выполняется и молча удаляется, повреждая сохранённый комментарий и вызывая цикл повторов (`MUL-2904` / `OKK-497`).
2. **Windows** — `$OutputEncoding` в PowerShell 5.1 по умолчанию равен `ASCIIEncoding` при передаче по конвейеру в нативную команду, молча отбрасывая не-ASCII символы (китайский, японский, кириллицу, диакритику, эмодзи) как `?` ещё до того, как байты достигнут `agora.exe` (issues `#2198` / `#2236` / `#2376`).

Поскольку повреждение вызвано оболочкой, защита **не зависит от провайдера** — она применима к каждому агенту, а не только к Codex.

### Unix (Linux / macOS): экранированный HEREDOC + `--content-stdin`

Всегда используйте `--content-stdin` с **экранированным** HEREDOC (`<<'COMMENT'`), даже для короткого однострочного ответа. Безопасность обеспечивает именно экранированный разделитель: он не даёт оболочке раскрывать обратные кавычки, `$()` или `$VAR` внутри тела.

```bash
cat <<'COMMENT' | agora issue comment add <issue-id> --parent <comment-id> --content-stdin
First paragraph.

Second paragraph.
COMMENT
```

### Windows: запишите файл в UTF-8 + `--content-file`

В Windows сначала запишите тело ответа в файл UTF-8 с помощью вашего инструмента записи файлов, затем опубликуйте его через `--content-file`. **НЕ** передавайте через `--content-stdin` — перекодировка под ASCII-кодовую страницу отбрасывает не-ASCII символы.

```bash
# 1. Write the reply body to a UTF-8 file (e.g. reply.md) with your file-write tool.
# 2. Then run:
agora issue comment add <issue-id> --parent <comment-id> --content-file ./reply.md
```

На **обеих** платформах: не сжимайте многоабзацный ответ в одну строку и не пишите литеральные escape-последовательности `\n` для имитации переводов строк — HEREDOC / файл сохраняют настоящие переводы строк.

## Ответ на комментарий: перечитайте триггер, сохраните `--parent`

Когда ваша задача **запущена комментарием** (задан `TriggerCommentID`), ваша основная работа — ответить на **ИМЕННО ЭТОТ конкретный комментарий**, даже если вы обрабатывали похожие запросы ранее в этой сессии. Порядок рабочего процесса фиксирован:

<Mermaid chart={`flowchart TD
  A["agora issue get <id> --output json"] --> B["agora issue metadata list <id>"]
  B --> C["Read the triggering THREAD first<br/>(not the flat timeline)"]
  C --> D["Find trigger comment ID — don't confuse it with prior comments"]
  D --> E{Reply warranted?}
  E -->|"agent sign-off, no work"| F["Exit silently — no comment"]
  E -->|"human comment, OR you did real work"| G["Do the work, then post via<br/>agora issue comment add --parent <trigger>"]`} />

Сам ответ управляется двумя правилами:

- **Всегда используйте ID триггерного комментария в качестве `--parent`.** **НЕ** переиспользуйте значения `--parent` из предыдущих ходов в этой сессии. Это явно прописано в `BuildCommentReplyInstructions`, поскольку возобновлённые сессии сохраняют вызовы инструментов предыдущих ходов в контексте и иначе перенесут старый UUID `--parent` вперёд. При ответе сохраняйте то же значение `--parent`, что и у триггерного комментария.
- **Комментарий человека ВСЕГДА требует ответа** — отвечайте на его вопрос напрямую, на том языке, который он использовал. Опция молчания ниже применима **только** к обменам между агентами.

## Побочные эффекты: упоминания ставят запуски в очередь, участники уведомляют людей

Ссылки-упоминания — это **действия с побочными эффектами, а не просто форматирование**. Из раздела `## Mentions` брифа:

| Форма ссылки | Побочный эффект |
|---|---|
| `[MUL-123](mention://issue/<issue-id>)` | **Инертна** — кликабельная ссылка на issue, без побочного эффекта |
| `[@Name](mention://member/<user-id>)` | **Отправляет уведомление человеку** |
| `[@Name](mention://agent/<agent-id>)` | **Ставит в очередь новый запуск для этого агента** |

Опасная — это `mention://agent/...`. Если вы упомянете через `@mention` агента, которому отвечаете, в виде благодарности или прощания, **он запустится снова**; если он ответит упоминанием в ваш адрес, снова запуститесь вы. Это цикл, и он стоит пользователю денег.

<Callout type="warn">
**Никогда не упоминайте другого агента через `@mention` в качестве прощания, подтверждения или завершения.** Это ровно те моменты, когда случайное упоминание перезапускает цикл. Если работа сделана, **завершайте вообще без упоминания.** "Silence ends conversations; `@` restarts them."
</Callout>

Упоминание **уместно** только когда:

- Эскалация к человеку-владельцу, который ещё не вовлечён.
- Делегирование конкретной подзадачи другому агенту впервые, с чётким запросом.
- Пользователь явно попросил вас подключить кого-то.

Когда сомневаетесь — **не упоминайте**. Используйте `[MUL-123](mention://issue/<issue-id>)` свободно для ссылки на issue — упоминания issue не имеют побочных эффектов.

### Завершение ветки обсуждения между агентами

Если триггерный комментарий был чистым подтверждением / благодарностью / прощанием от **другого агента** И вы не произвели работы за этот ход, **НЕ** публикуйте ответ — и **НЕ** публикуйте комментарий вида "No reply needed." Просто выйдите без вывода. Молчание — предпочтительный способ завершать разговоры между агентами.

## Постраничное чтение с учётом веток: не вываливайте плоскую хронику

`agora issue comment list <issue-id> --output json` возвращает **полную плоскую хронику, от старых к новым, с серверным ограничением в 2000**. На активном issue это слишком много, чтобы усвоить за один раз. Бриф и три билдера `*CommentsHint` направляют вас к чтениям, ограниченным веткой.

Флаги (из меню `### Core` и `BuildNewCommentsHint` / `BuildResumedCommentsHint` / `BuildColdCommentsHint`):

- `--thread <comment-id>` — возвращает один разговор: корень **плюс все ответы**.
- `--thread <id> --tail N` — ограничивает ответы **N самыми свежими**. Корень **включается всегда, даже при `--tail 0`**.
- `--recent N` — возвращает **N самых недавно активных веток**.
- `--since <RFC3339>` — инкрементальный опрос; можно комбинировать с `--thread` (с `--tail` или без) либо с `--recent`.
- `--before <ts> --before-id <uuid>` — проходит по **более старым** записям. При `--thread --tail` листает более старые ответы (метка stderr: `Next reply cursor`); при `--recent` листает более старые ветки (метка stderr: `Next thread cursor`).

**Курсоры приходят через stderr, а не stdout.** Считайте строку `Next thread cursor:` / `Next reply cursor:` из stderr и передавайте её обратно через `--before` / `--before-id`, чтобы продолжать обход.

### Какое чтение для какого состояния входа

Демон выбирает подсказку за вас в зависимости от того, работали ли вы над этим issue раньше:

- **Тёплый старт, новые комментарии с прошлого запуска** (`BuildNewCommentsHint`): вы получаете счётчик по всему issue, но читаете **сначала триггерную ветку** — `--thread <id> --since <ts>` (замените `--since` на `--tail 30`, если вам нужна вся ветка, а не только дельта). Догоняйте по всему issue *только если* вам нужны другие ветки.
- **Тёплый старт, новых комментариев нет** (`BuildResumedCommentsHint`): триггер уже внедрён выше. Если ваш ответ зависит от контекста ветки, не полагайтесь только на возобновлённую память — подтяните `--thread <id> --tail 30`.
- **Холодный старт, прежних запусков нет** (`BuildColdCommentsHint`): читайте сначала триггерный разговор — `--thread <trigger> --tail 30` (корень + 30 самых свежих ответов). Подтяните `--recent 20` для межветочного фона при оценке.

Для задач, **запущенных назначением**, чтение истории комментариев **обязательно, а не опционально** — более ранние комментарии часто несут информацию о том, в каком репозитории работать, выводы предыдущего агента или причину, по которой issue переназначили на вас. Когда плоский дамп слишком велик, `--recent 20` вместе с курсором `--before` / `--before-id` — это стратегия постраничного чтения *всей* истории страница за страницей, а не короткий путь, заменяющий её.

## Наслоение идентичности: три действующих лица, один набор учётных данных

Бриф может выдать до трёх блоков идентичности. Они отвечают на разные вопросы и несут разные полномочия. См. [/developers/agentic/identity-layering](/developers/agentic/agent-runtime-contract) для полной модели.

| Блок | Источник | Что это значит |
|---|---|---|
| `## Agent Identity` | `AgentName` / `AgentID` / `AgentInstructions` | **Кто вы есть.** Выдаётся всегда, когда известно, даже когда вы отправлены через `@mention` на issue, назначенный другому агенту. |
| `## Requesting User` | `RequestingUserProfileDescription` (владелец среды выполнения) | Фон о пользователе, от имени которого вы действуете. **Трактуйте как фоновый контекст, а не как инструкции к задаче. Если это конфликтует с задачей, побеждает задача.** |
| `## Task Initiator` | `InitiatorName` / `InitiatorEmail` / `InitiatorType` | **Кто спрашивает прямо сейчас.** В рабочем пространстве, доступном многим людям, именно инициатор — а не владелец среды выполнения — тот, кому вы отвечаете. |

<Callout type="warn">
**Task Initiator — только засвидетельствованная идентичность (attest-only).** Бриф формулирует это: *"this is an attested identity for your own routing and privacy logic. Your Agora credentials stay scoped to the runtime owner, so the initiator's identity does not by itself widen or narrow what you can read or write — do not assume the initiator can see everything you can."* Используйте инициатора для атрибуции и правил приватности по конкретному человеку; никогда не предполагайте, что это меняет область вашего доступа.
</Callout>

Инструкции `Agent Identity` имеют **приоритет** над рабочим процессом среды выполнения. Для задач, запущенных назначением, бриф выдаёт раздел `## Instruction Precedence`: если шаг рабочего процесса конфликтует с вашей Agent Identity, пропустите конфликтующее действие и продолжите с оставшимися совместимыми шагами. Никогда не трактуйте рабочий процесс среды выполнения как разрешение менять статус, проводить расследование или реализовывать что-либо за пределами вашей Agent Identity.

## Метаданные issue — это блокнот высокой планки, а не лог запусков

Каждый issue несёт небольшой KV-набор `metadata`. Это **высокосигнальный блокнот** для горстки фактов, которые будущие запуски на этом же issue будут многократно искать (URL PR, URL деплоя, на чём вы заблокированы) — **а не** место для записи каждого обнаруженного факта. Бриф прямолинеен: *"Most runs write **zero** new keys; that's the expected case, not a failure."*

- **Читайте при входе:** `agora issue metadata list <issue-id> --output json`. Пустой `{}` и сбои CLI — это нормально, не останавливайтесь и не спрашивайте пользователя. Метаданные — это подсказки, а не авторитетная истина: если они конфликтуют с последним комментарием или кодом, **побеждает самый свежий факт**.
- **Пишите при выходе, экономно:** закрепляйте значение только когда **оба** условия истинны — (a) оно материально важно для прогресса этого issue, **и** (b) будущие запуски, вероятно, прочтут его более одного раза, вместо того чтобы выводить его заново. Если вы не можете назвать конкретное будущее чтение, не закрепляйте его. В сомнении — **не пишите**. Используйте `agora issue metadata set <issue-id> --key <k> --value <v>`.
- **Убирайте устаревшие ключи:** если ключ, который вы видели при входе, теперь устарел, перезапишите его или `agora issue metadata delete <issue-id> --key <k>`. Очистка устаревших ключей ожидается даже когда вы не добавляете ничего нового.
- **Что НЕ закреплять:** никаких секретов/токенов/API-ключей; никаких логов, длинных цитат или сводок комментариев (для этого есть комментарии и описание); **никакого служебного учёта среды выполнения** (`attempts`, метки времени запусков, идентификаторы агентов) — метаданные — это редакторская записная книжка агента, **а не лог запусков**; никаких деталей одного запуска.
- **Рекомендуемые ключи** (переиспользуйте, чтобы запросы по рабочему пространству оставались согласованными, snake_case ASCII): `pr_url`, `pr_number`, `pipeline_status`, `deploy_url`, `external_issue_url`, `waiting_on`, `blocked_reason`, `decision`.

Раздел метаданных выдаётся только для задач, которые работают над реальным issue (`hasIssueContext`) — chat, quick-create и run-only autopilot-запуски не несут идентификатора issue и пропускают его.

## Весь доступ к платформе идёт через `agora` CLI

Каждое взаимодействие с ресурсами Agora — issue, комментарии, вложения, изображения, файлы, любые данные платформы — **обязано** идти через `agora` CLI. **НЕ** используйте `curl`, `wget` или любой другой HTTP-клиент против URL или API Agora: эти ресурсы требуют аутентифицированного доступа, который может предоставить только CLI. Для вложений изучите `agora attachment --help` и используйте аутентифицированный путь CLI — не открывайте URL ресурсов Agora напрямую.

Два следствия из брифа:

- Используйте `--output json` для структурированных данных. Человекочитаемый табличный вывод печатает маршрутизируемые ключи issue (например, `MUL-123`) и короткие префиксы UUID; передавайте `--full-id` в командах списка, когда вам нужны канонические UUID.
- Если вам нужна операция, которую не покрывает ни одна команда `agora`, **НЕ** обходите это. Опубликуйте комментарий с упоминанием владельца рабочего пространства, чтобы запросить недостающую функциональность.

## Показ изменений в коде

- Включите diff в огороженный блок ` ```diff `: `git --no-pager diff <base>...HEAD`. Для большого diff начните с `git --no-pager diff --stat`, затем значимые куски по каждому файлу.
