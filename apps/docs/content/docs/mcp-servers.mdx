## Connect Claude Code and other clients to Agora

Agora also provides its own workspace MCP server: **`agora mcp serve`**. This is the opposite direction from the workspace's external MCP connectors below: a client such as Claude Code can read Agora tasks, projects, comments, and knowledge through your authenticated CLI.

Use a CLI build that includes `mcp serve` (`agora mcp serve --help`). Authenticate before connecting, then bind the server to an explicit workspace UUID:

```bash
agora login
claude mcp add --transport stdio agora -- agora mcp serve --workspace-id YOUR_WORKSPACE_UUID
claude mcp get agora
```

Inside Claude Code, open `/mcp` to verify the connection. The command follows [Claude Code's stdio setup](https://code.claude.com/docs/en/mcp#option-3-add-a-local-stdio-server). If the CLI is not on the client's `PATH`, replace the second `agora` with its absolute executable path.

For Claude Desktop, Cursor, and other clients that accept `mcpServers` JSON:

```json
{
  "mcpServers": {
    "agora": {
      "command": "agora",
      "args": ["mcp", "serve", "--workspace-id", "YOUR_WORKSPACE_UUID"]
    }
  }
}
```

The CLI reuses your saved login and server URL. `--profile` selects an isolated CLI profile; `--server-url`, `AGORA_SERVER_URL`, `AGORA_WORKSPACE_ID`, and `AGORA_TOKEN` work as with other Agora commands. Keep tokens out of committed MCP JSON and command arguments. Log in separately rather than trying to perform interactive authentication on the MCP protocol stream.

### Available Agora tools

| Area | Tools |
| --- | --- |
| Workspace and projects | `get_workspace`, `list_projects`, `get_project` |
| Tasks and discussion | `list_issues`, `search_issues`, `get_issue`, `list_comments` |
| Knowledge and requirements | `list_knowledge`, `search_knowledge`, `get_knowledge`, `list_project_knowledge` |
| Assignment metadata | `list_labels`, `list_members`, `list_agents` |
| Optional writes | `create_issue`, `update_issue`, `comment_issue` |

The default exposes **14 read-only tools** and rejects write calls even if a client guesses their names. To enable the three task-writing tools, deliberately add `--allow-writes` to the command or JSON `args` and reconnect:

```bash
agora mcp serve --workspace-id YOUR_WORKSPACE_UUID --allow-writes
```

<Callout type="warning">
Writes use your existing Agora permissions and may trigger normal workspace automations, agent execution, and notifications. The flag enables writes for the entire MCP session; it is not per-action confirmation. Configure approvals in your MCP client. Never automatically retry a failed write: inspect Agora first because the request may already have succeeded. No delete, credential-management, shell, or arbitrary-HTTP tools are exposed.
</Callout>

For recommendation-only reviews, keep the default and ask: "Check this behavior against Agora knowledge. Separate confirmed bugs, regression risks, and missing evidence. Recommend tasks without creating them." `list_project_knowledge` returns only reviewed, active knowledge items. `search_knowledge` returns source IDs and citation references; read the document before treating a snippet as a requirement. Agent listings contain only assignment metadata, never runtime configuration or MCP credentials.

This is a local **stdio** connection to the Agora REST API, not a hosted HTTP/OAuth MCP endpoint. It implements MCP tool discovery/calls, initialization, ping, cancellation, and bounded request deadlines. The existing `agora mcp qa` command remains a separate test-runner server.

## Connect Agora agents to external tools

Agora accepts the same top-level `mcpServers` JSON shape used by Claude Desktop and Cursor. Open **Workspace → MCP servers** to paste or import an `mcp.json` file.

```json
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/workspace"]
    },
    "linear": {
      "type": "http",
      "url": "https://mcp.linear.app/mcp",
      "headers": { "Authorization": "Bearer ${LINEAR_TOKEN}" }
    }
  }
}
```

## Shared defaults and agent overrides

There are two configuration layers:

1. **Workspace `mcp.json`** — a project-wide default merged into every agent when a new task starts. Only workspace owners and admins can read or change it.
2. **Agent-specific connections** — servers attached to selected agents. If an agent and the workspace both define the same server name, the agent entry wins.

Saving a change affects **new tasks**. It does not rewrite the configuration of a task that is already running.

The workspace document is stored separately from the ordinary workspace response because commands, environment variables, URLs, and headers may contain sensitive values. Updates are audit logged by server name without recording server definitions.

<Callout type="warning">
Values pasted into `env` and `headers` are visible to workspace owners and admins. For a remote bearer token, use the **sealed auth** field in the agent-specific server form; Agora stores that secret separately and injects it only when dispatching a task.
</Callout>

## MCP servers vs. plugins

- **MCP server** — one direct connection to a live tool or data source. Use it when you already have an `mcp.json` entry or need one connector.
- **Plugin** — a reusable capability bundle containing workspace skills and optionally one or more MCP connectors. Install or uninstall the bundle on selected agents as a unit.
- **Skill** — instructions and supporting files that teach an agent how to perform a kind of work; it is not a live connection.

Use a shared MCP default for infrastructure every agent should reach. Use an agent override for a specialist or different credentials. Use a plugin when the connection and operating instructions should travel together.

## Runtime delivery

Agora translates the shared JSON into each supported runtime's native mechanism: Claude receives an MCP config at launch, Cursor gets `.cursor/mcp.json`, Codex gets managed `mcp_servers` entries, ACP runtimes receive `mcpServers`, and OpenCode/OpenClaw receive their runtime-specific config.

MCP support remains provider-specific. Check [AI coding tools comparison](/providers) before relying on a server for a particular agent.

## Troubleshooting

- A server name may contain only letters, numbers, `_`, and `-`.
- A local server needs a non-empty `command`; `args` must be an array of strings and `env` must contain string values.
- A remote server needs a non-empty `url`; `headers` must contain string values.
- If a shared server seems missing, check whether the agent defines the same name and therefore overrides it.
- If a config saves but the tool is unavailable, confirm that the agent's runtime supports MCP and that the command exists on the daemon machine.
