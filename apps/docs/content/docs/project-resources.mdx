---
title: Project Resources
description: Attach typed pointers (Git repos, local directories, more later) to a project so agents can pick them up as scoped context.
---

A **Project Resource** is a typed pointer — a Git repo URL, a path on your own machine, a Notion page tomorrow — attached to a [project](/workspaces). When an [agent](/agents) runs against an issue inside that project, the daemon automatically writes the project's resource list into the agent's working directory and into its [meta-skill](/skills) prompt.

The result: the agent knows which repo to check out (or which local directory to work in), and which docs are the "primary references" for this project, without anyone copy-pasting context into the issue body.

## Mental model

A project is no longer just a label. It is a small **resource container**:

- A project has 0..N **resources**.
- A resource has a `resource_type` (e.g. `github_repo`, `local_directory`) and a `resource_ref` (a JSON payload typed by `resource_type`).
- New resource types add a string + a handler. **No schema migration. No frontend rewrite.**

This shape is intentional — it's the same pattern Agora already uses for agent providers: a `type` discriminator and a typed payload. It keeps the schema stable so adding "Notion page", "Google Doc", "uploaded file", or "external URL" later is a small, additive change.

Today two resource types ship: [`github_repo`](#resource-type-github_repo) (clone-per-task into an isolated worktree) and [`local_directory`](#resource-type-local_directory) (work against a folder that already exists on a specific daemon's machine — in place, or in a worktree cut from it).

## Resource type: `github_repo`

The default resource type — checked out per task into an isolated worktree:

```json
{
  "resource_type": "github_repo",
  "resource_ref": {
    "url": "https://github.com/owner/repo",
    "default_branch_hint": "main"
  }
}
```

`default_branch_hint` is optional — if present, the daemon surfaces it in the meta-skill so the agent knows which branch to base its work on.

## Resource type: `local_directory`

For repos that can't reasonably be re-cloned per task — multi-gigabyte game checkouts, large monorepos, or any project where the worktree-per-task model is painful — a project can instead point at an **existing directory on a specific [daemon](/daemon-runtimes)'s machine**. The agent runs **directly inside that folder**, with no clone, no copy, and no worktree.

```json
{
  "resource_type": "local_directory",
  "resource_ref": {
    "local_path": "/Users/me/code/big-game",
    "daemon_id": "0001234e-…",
    "label": "main checkout",
    "isolation": "in_place",
    "access": "write",
    "preview_url": "http://localhost:3000"
  }
}
```

Only `local_path` and `daemon_id` are required. The other three are the knobs that decide how the agent works in the folder — [`isolation` and `access`](#how-the-agent-works-in-the-folder-isolation--access) and [`preview_url`](#preview-point-qa-at-your-own-dev-server) — each covered below.

The trade-off vs. `github_repo` is intentional: only the bound daemon can pick up tasks against the directory. In exchange you keep your existing checkout, your existing branch, your existing dirty state — Agora never re-clones it.

### When to pick `local_directory` over `github_repo`

| Concern | `github_repo` (worktree) | `local_directory` |
| --- | --- | --- |
| Checkout cost per task | Fresh clone + worktree | None — the code is already there |
| Concurrency on the same repo | Many tasks in parallel | Serial with `in_place`; parallel per issue with `isolation: worktree` |
| Branch / dirty state | Each task gets a fresh branch from the default | `in_place`: agent commits go on an isolated `agent/…` branch off your current HEAD, dirty tracked state snapshotted first. `worktree`: your checkout isn't touched at all |
| Where it can run | Any daemon | Exactly one daemon (the one bound) |
| Disk footprint | One worktree per task | Zero for `in_place`; one worktree per issue for `worktree` |

The one-line rule: **reach for `local_directory` when the code is already on a machine and getting it again is the expensive part** — or when you want to watch the work land in the checkout you already have open.

### Use cases

Concrete situations where teams reach for this, and what to set for each.

#### 1. The repo is too big to clone per task

A multi-gigabyte game checkout, a monorepo with heavy LFS assets, a project whose `npm install` takes ten minutes. The per-task `git clone` would dominate the actual work.

Attach the checkout with the defaults (`in_place`, `write`). The agent runs in the folder you already have — no clone, no copy, no second copy of the assets on disk.

#### 2. You want to watch the agent work in your own editor

You're iterating on one component and want to flip between the agent's edits and your editor every few minutes, rather than digging a per-task worktree out of `~/agora_workspaces/`.

Defaults again. The agent's commits land on an `agent/…` branch cut from your `HEAD`, so your branch never moves and you can review the diff in place.

#### 3. A reference codebase the agent must read but never touch

An old monolith, a vendor SDK, a sibling service whose API you're integrating against — you want the agent to *learn* from the code, not edit it.

Set **`access: read`**. The folder becomes reference material: the agent reads it through an isolated worktree and every write-back path into your checkout is disabled. Safer than trusting a prompt to say "don't edit this."

#### 4. Several issues in flight on one checkout

Three agents on three issues, one local repo. With the default `in_place` they queue behind each other — correct, but slow.

Set **`isolation: worktree`**. Each issue gets its own git worktree cut from your checkout, so issues run in parallel and your working tree stays untouched.

#### 5. QA should test the app you already have running

Your dev server is up on `localhost:3000` with the exact state you're debugging, and you don't want QA to spawn a second one.

Set **`preview_url: http://localhost:3000`**. The issue's Preview surface proxies to your server, so reviewers and the QA agent see precisely what you see.

#### 6. A team where everyone works locally

A shared project, and each teammate wants agents to run on their own machine.

Each person attaches **their own** ordered `local_directory` set — a primary folder plus any related folders on their own host. A task runs on the daemon that owns the receiving agent's runtime, and that daemon uses only rows matching its own ID. Nobody's folders are visible to anyone else's daemon.

#### When *not* to use it

If any daemon should be able to pick up the work, and cloning is cheap, stay on `github_repo`. `local_directory` binds the work to one machine — that's the whole point, and it's a cost when the machine is asleep.

### Attaching a local directory

Three ways, depending on where you are. All three end at the same resource row — pick whichever is in front of you.

#### From the web

Open the project → **Resources** panel → **Add local folder**.

1. **Machine** — pick which host holds the code, from the workspace's online daemons. (A machine you can't use doesn't appear; see [who can attach one](#who-can-attach-one).)
2. **Folder** — click **Browse** to walk that machine's folders, or type an absolute path if you already know it.
3. **Access** — *Read & write* (default) or *Read-only*. See [`isolation` + `access`](#how-the-agent-works-in-the-folder-isolation--access).
4. **Preview URL** — optional; your own dev server, e.g. `http://localhost:3000`.
5. **Attach folder**.

The web attach does **not** record approval — the machine's owner still has to approve the path with `agora daemon allow-dir` before tasks run there. See [owner approval](#owner-approval-on-the-machine).

#### The folder browser

A browser cannot open an OS folder picker for *another* machine — and even for your own, `<input type="file">` never hands JavaScript an absolute path. So **Browse** asks the daemon to list its own directories instead, one level at a time. You navigate the machine's real folders, and Agora gets the real path.

What you'll see:

- **Only folders**, since a folder is what you're attaching. Git repositories are badged **repo**, so a checkout is obvious at a glance.
- **Starting at the machine's home directory.** You can go up until you hit the top of what the machine shares — no further.
- **Only what the machine offers**: the daemon serves its home directory plus any folder its owner has already approved. Everything else is refused, so a picker cannot be used to read someone's whole disk.
- **Nothing sensitive.** Credential and OS stores — `~/.ssh`, `~/.aws`, `~/Library`, `AppData`, dot-directories under `$HOME` — are never listed and cannot be opened, so no row leads to a dead end.

**Browsing is not approval.** The listing is read-only and grants nothing: seeing a folder in the picker doesn't let an agent run in it. Approval is a separate, deliberate act by the machine's owner.

If the machine is switched off, the picker says so rather than hanging — start its daemon, or type the path and attach now, approve later.

<Callout type="info">
The folder browser needs the machine's daemon on **v0.3.50 or newer** — the listing is served by the daemon itself, not the backend. Against an older daemon the browser shows the error inline; type the path directly, or update that machine's CLI.
</Callout>

#### From the Desktop app

Open the project → **Resources** → **Add local directory**. A native folder picker opens, bound to **the daemon this Desktop install registers**.

Picking the folder also records your **owner approval** automatically — you're sitting at the machine, so consent is implicit. This is the only route where attach and approve happen in one step.

The button is **disabled with a hint** only when this machine's daemon is offline. You can pick it repeatedly to attach a primary folder and any number of related folders on the same machine; every pick also records owner approval.

#### From the CLI

Useful for headless hosts, scripts, and any machine you're already SSH'd into:

```bash
agora project resource add <project-id> \
  --type local_directory \
  --local-path /Users/me/code/big-game \
  --daemon-id <daemon-uuid> \
  --ref-label "main checkout"        # optional

agora project resource update <project-id> <resource-id> \
  --local-path /Users/me/code/big-game-new
```

`--daemon-id` comes from `agora daemon list`. The CLI also accepts the generic `--ref '<json>'` escape hatch if you'd rather pass the payload directly — that's how you set `isolation`, `access`, or `preview_url` from the command line:

```bash
agora project resource add <project-id> \
  --type local_directory \
  --ref '{"local_path":"/srv/legacy","daemon_id":"<daemon-uuid>","access":"read","isolation":"worktree"}'
```

### Who can attach one

`local_directory` mutations are **human-only**. Any create, update, or delete of a `local_directory` resource made with a machine credential — an agent's task token or a cloud-node PAT — returns `403`, including the bundled path where resources ride along on project create. An agent can never bind itself (or another agent) to a folder on your machine; if a task genuinely needs a local directory, the agent should ask you to attach it. `github_repo` resources are unaffected — agents keep creating those as part of normal repo bootstrap.

The `daemon_id` is validated at attach time and again whenever the `resource_ref` changes:

- It must match a daemon runtime **registered in the workspace** — an unknown or typo'd daemon ID is rejected with `400`.
- The runtime must be one **you are allowed to use**: you own it, it's shared (`visibility=public`), or you're a workspace owner/admin. Pointing a resource at another member's private daemon is rejected with `403`.

This is the same ownership rule that governs binding an agent to a runtime, applied to the machine the directory lives on.

### Owner approval on the machine

Attaching the resource is not enough by itself: **the machine's owner must approve the folder on that machine** before the daemon will run tasks in it. The resource row lives on the server and could be created by anyone with your workspace credentials — the approval lives on the executing machine, where only its owner can put it. Three ways to approve:

- **Desktop folder picker** — picking the folder records the approval automatically. For the normal flow you never think about this.
- **`agora daemon allow-dir <path>`** — run on the daemon host as the OS user the daemon runs as. Approvals are stored in `~/.agora/local-dirs.json` and re-read on every task, so no daemon restart is needed.
- **`AGORA_LOCAL_DIR_ALLOWLIST`** — a path-list-separated list of absolute paths, for headless or containerized daemons where neither the picker nor a CLI round-trip exists.

Approving a folder covers everything beneath it. A task against an unapproved path fails fast with a message that names the exact `allow-dir` command to run — approve and re-dispatch, nothing else to clean up.

**Attaching from the web or the CLI always needs a manual approval**, because no picker ran on the daemon host. That includes a folder you found with the web [folder browser](#the-folder-browser): browsing is a read-only listing and grants nothing. The split is deliberate — attaching is a workspace action anyone with your credentials could take, while approving is a local act by the person sitting at the machine. Only the Desktop picker collapses the two, because there the two people are the same person.

Manage approvals on the daemon host with `agora daemon list-dirs` (show what's approved, file and env sources) and `agora daemon revoke-dir <path>` (remove a file approval; env approvals are revoked by unsetting `AGORA_LOCAL_DIR_ALLOWLIST`).

### How the agent works in the folder: `isolation` + `access`

Two fields decide what the agent may do with your checkout. Both default to the original behaviour, so a resource attached before they existed keeps working unchanged.

**`isolation`** — where the agent's working tree comes from:

| Value | What happens | Use when |
| --- | --- | --- |
| `in_place` *(default)* | The agent works **directly in your folder**. Commits go on an isolated `agent/<name>/<task>` branch cut from your `HEAD`; your branch ref never moves. Tasks on the folder run **one at a time**. | You want to watch the work land in the checkout you already have open. |
| `worktree` | The agent works in an isolated **git worktree cut from your checkout**, kept under `~/agora_workspaces/<ws>/.worktrees/<issue>/` — outside your folder. Your working tree is never touched. One worktree per issue, reused across that issue's dev → QA → fix tasks, so **different issues run in parallel**. | Several issues are in flight on one checkout, or you want your tree left alone. |

**`access`** — what the agent may do:

| Value | What happens |
| --- | --- |
| `write` *(default)* | The agent may modify the folder — in-place edits, or worktree write-back. |
| `read` | The folder is **reference material only**. Every write-back path into your checkout is disabled, and the agent reads it through a detached worktree. |

`access: read` **forces `isolation: worktree`** — running in place is inherently a write. The API rejects `read` + `in_place` with a `400` rather than silently "fixing" it, and the daemon forces worktree mode even if an older ref slips through, so a read-only folder can never be handed to an agent in place.

In the web UI these are the **Read & write / Read-only** toggle on the attach form and on each resource row. Flipping a row to *Read-only* switches it to worktree isolation at the same time.

<Callout type="warning">
There is no file-level write lock. For `in_place`, the per-folder serial gate — one task at a time — is the only thing stopping agents on two issues from touching the same files at once. If you need real parallelism on one checkout, use `isolation: worktree` (each issue gets its own tree) rather than pointing two issues at the same in-place folder.
</Callout>

### Preview: point QA at your own dev server

`preview_url` is your **own locally-running dev server** — the one you already have up while you work:

```json
"preview_url": "http://localhost:3000"
```

When set, the issue's **Preview** surface proxies to that server instead of spawning one. Reviewers and the QA agent see exactly the app you see, in the state you're running it — no second server, no waiting for a build.

- Only `localhost`, `127.0.0.1`, `::1`, and private-LAN addresses are accepted. The **daemon** reaches your server, not the public internet — the URL never has to be routable from outside your machine.
- Leave it empty and Preview falls back to starting the project's dev server itself (the detection described under [QA on a local directory](#qa-on-a-local-directory)).
- Set it from the web via the **screen icon** on the resource row, or with `--ref` from the CLI.

If your server isn't running when someone opens Preview, the surface simply reports that it can't reach it — nothing is started behind your back.

For a completed orchestration artifact, Preview must run the exact integrated
HEAD rather than your mutable working tree. Agora creates a disposable detached
runtime and starts it with the project's **Workflow → Advanced orchestration →
Preview & checks → Start command** (`qa_smoke_cmd`). The Checks tab uses the
project's Test command (`qa_test_cmd`). When either field is empty, Agora falls
back to repository detection. The Preview header shows whether the effective
command came from the project workflow, a local resource URL, or auto-detection.

Multi-root projects can add **repository / folder overrides** in the same
section. Each override matches the name in the Preview repository selector and
can set a relative working directory, start command, and test command. The
project-level commands remain the fallback for repositories without an
override. Startup output is streamed into Preview while Agora waits for the
local port; the iframe is mounted only after that port is reachable.

`PROJECT.md` remains human/agent guidance and can explain the same local setup,
but Agora never extracts and executes shell commands from prose. Put executable
commands in the structured project workflow fields so they are explicit,
reviewable, and signed into the artifact capability.

### Path rules

The path you attach must clear both an attach-time and a per-task validation. Both are enforced by the daemon that owns the resource — the server validates who may attach and which daemon the ref points at (see above), but never inspects the path itself. A path that breaks any rule fails the task with a typed error and leaves your directory untouched:

- Must be **absolute**.
- Must **exist** and be a **directory** (not a file, symlink to a file, or device node).
- Must be **readable and writable** by the daemon process.
- Cannot be a system root or an entire user profile — `/`, `/Users`, `/home`, `/root`, `/etc`, `/tmp`, `/var`, `/usr`, `/opt`, `/Users/Shared`, your own `$HOME`, any Windows drive root (`C:\`, `D:\`, …), or `C:\Users` / `C:\ProgramData` / `C:\Program Files` / `C:\Program Files (x86)` / `C:\Windows`.
- Cannot be inside a **protected home subtree**: any dot-directory directly under `$HOME` (`~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.config`, …), `~/Library` on macOS, or `AppData` on Windows. These hold credentials and OS-managed state, never projects — and agents run with permission prompts bypassed, so handing one an agent is handing over the credential store.
- A symlink that resolves to any of the above is rejected, and so is the canonical form of an OS-aliased path (e.g. on macOS, typing `/private/tmp` is rejected the same way as `/tmp`).

The blacklist is intentionally aggressive — picking your home directory would put Agora's runtime files at the root of your account, which is never what you want. Pick a sub-folder (typically your actual project checkout) instead.

### Primary and additional folders per daemon

A project may hold **multiple `local_directory` resources on the same daemon**. The first position-ordered folder is the **primary** folder: it becomes the task working directory. Later folders are additional project roots that the agent can read and write. Use the star action in Resources to promote any folder to primary. Deleting the primary automatically makes the next folder primary.

The API rejects only a duplicate of the same daemon and path with `409`. Symlink aliases that resolve to the same real directory are rejected by the daemon at task start. Different daemons remain independent, so teammates can attach their own ordered folder sets on their own machines.

### Mixing resource types, and multiple `local_directory` resources

Two cross-resource configurations show up in practice:

- **`github_repo` + `local_directory` on the same project.** On the daemon that has a matching `local_directory` binding, the local directory **takes precedence**: the agent runs in your folder, and the daemon does not create or use a `github_repo` worktree for that task. The agent's brief is also rewritten for in-place mode — instead of the usual "`agora repo checkout <url>`" guidance it gets a **Working Directory (local, in-place)** section telling it the code is already present and to edit files directly, **not** to run `agora repo checkout` (which would nest a redundant worktree inside your folder). The `github_repo` URLs are still listed for reference in `.agora/project/resources.json` and the brief, marked as "already represented by the directory you're in — do not check them out." On a daemon that has **no** `local_directory` row for this project (different machine, or before that teammate attached one), the task falls back to the usual `github_repo` worktree flow. Effectively the local directory is a per-daemon override of the worktree path.
- **Multiple `local_directory` resources on the same project.** A task lands on the daemon that owns the receiving agent's runtime. That daemon uses every matching row as one ordered project corpus, ignores rows for other machines, and starts the agent in the primary folder. This is not load-balancing; choose an agent bound to the machine where the folders exist.

A daemon that has no `local_directory` row for a project that has one bound elsewhere is **not** blocked — its tasks simply proceed via the project's other resources (typically the `github_repo` fallback). The `local_directory` only matters for the daemon it's bound to.

### Running tasks against a local directory

When a task is dispatched on an issue whose project has one or more `local_directory` resources bound to the receiving daemon, the daemon:

1. Re-validates and owner-approval-checks every path (rules above).
2. Acquires every per-directory lock in deterministic path order, keyed on symlink-resolved real paths. This prevents overlapping tasks and cross-folder lock deadlocks.
3. Writes the agent's `CLAUDE.md` / `AGENTS.md` (and `.agora/project/resources.json`) into the **primary** directory. The agent starts there and receives the complete additional-folder list. Codex also receives those paths through its `workspace-write` writable-roots sandbox setting.
4. Keeps Agora's runtime artefacts (`output/`, `logs/`, `.gc_meta.json`) in a separate envRoot **outside** the user's directory.

If any folder selects `worktree` isolation or read-only access, Agora fail-safely provisions the whole attached set as sibling issue worktrees. Otherwise all folders run in place and all of their locks are held for the task. Repository retrieval ranks files from every attached root under one shared per-task evidence budget.

If a second task for the same directory arrives while the first is running, it parks with status **Waiting for local directory** (等待本地目录释放). The status is visible everywhere the task is — the chat task pill, the agent banner, the execution log, and the activity indicator — and the parked task counts toward the agent's "queued" presence. Cancelling the parked task releases its slot immediately; cancelling the running task lets the next one promote.

The wait is not a timeout — a parked task stays parked until either the lock releases or the user / agent cancels it.

### What Agora will and won't touch in your directory

- **Will write** `CLAUDE.md` / `AGENTS.md` (or the equivalent for your agent's provider) and `.agora/project/resources.json` at the directory root, so the agent has its meta-skill and resource list. Add these to your `.gitignore` if you don't want them committed.
- **Will write** whatever code edits the agent decides to make — exactly the same way as if you'd run the agent locally yourself.
- **Will never physically delete** the directory or anything inside it. Garbage collection is path-aware: for `local_directory` envRoots it cleans only its own `output/` and `logs/` under `workspacesRoot`, and treats the user's directory as off-limits.

### Git safety (when the directory is a git repo)

If the folder is a git work tree, the daemon protects your branch and your uncommitted work automatically:

- **Your commits stay yours.** Before the agent runs, the daemon creates an isolated branch `agent/<agent-name>/<short-task-id>` from your current `HEAD` and checks it out. The agent's commits land there, never on your branch. Your branch ref is never moved.
- **Read-only runs leave no trace.** If the agent makes no commits (a QA gate, an inspection), the daemon deletes that branch and puts you back on your original branch when the task ends — the repo is exactly where you left it.
- **When the agent did commit, you stay on the agent branch** so you can review the work in place. The task's result comment tells you the branch name and the one-liner to get back (`git checkout <your-branch>`). Switching back is left to you on purpose — the daemon never rewrites your working-tree files out from under you after a real run.
- **Dirty work is backed up.** If your tree has uncommitted tracked changes when the agent starts, the daemon snapshots them to `refs/agora/backup/<short-task-id>` with `git stash create` — a zero-touch backup that moves no files. Recover with `git stash apply <ref>` (the recovery command is printed in the result comment). Untracked files are **not** captured by this snapshot.
- Plain (non-git) folders skip all of the above and run exactly in place, as before.

### QA on a local directory

When the workspace has `labs.qa_dev_runtimes` enabled, the automatic QA gate (fired when an issue moves to `in_review`) knows how to test an app that only exists in your local folder:

- **The QA task runs on your machine.** If the issue's project has a `local_directory` bound to an online daemon, the gate pins the QA task to that daemon — the only place where the app's `127.0.0.1` is reachable. It ranks behind a concrete declared `dev_apps` URL but ahead of a deployed QA box.
- **The app is started for you.** The QA agent brings the app up through the daemon's dev-server preview (the same detection covered under "Preview"), then smokes the resulting `http://127.0.0.1:<port>/`. Set the project's QA smoke command if the app needs a specific launch command.
- **Your tree is never touched for QA.** The QA agent is told never to switch branches or edit files in your folder; it builds its comparison baseline in a throwaway `git worktree` off to the side. Combined with the git-safety branch handling above, a QA run leaves your working directory exactly as it was.
- **It queues behind your own work.** Because tasks on one folder are serialized, a QA gate waits for your in-flight dev task on the same directory to finish, then runs — you'll see `waiting_local_directory` until it acquires.

Watching the QA agent drive a browser live works when your daemon is reachable from the backend (self-host, or a laptop on the mesh). Cloud-backend live-watch of a laptop app is a separate mesh setup.

### v1 limits (will tighten in follow-ups)

The first release deliberately ships with sharper edges than `github_repo`. Expect this list to shrink over time — what's documented here is what's true today:

- **Untracked files aren't snapshotted.** The dirty-tree backup captures tracked modifications only; an agent that overwrites or deletes an untracked file leaves nothing to recover from. Commit or stash untracked work you care about before a risky run. (Applies to `in_place`; with `isolation: worktree` the agent never works in your tree at all.)
- **You're left on the agent branch after a run with commits.** The daemon doesn't switch you back automatically (that would rewrite your working tree). The result comment gives you the return command.
- **No automatic PR.** When the task ends, the changes sit on the agent branch — nothing is pushed and no PR is opened. Push and open the PR yourself when you're ready.
- **`waiting_local_directory` shows status, not the holder.** The badge tells you the task is parked; it doesn't surface which task or which file path is currently holding the directory.
- **The folder browser lists, it doesn't search.** There's no filter box or "recent folders" — you walk the tree, or paste a path you already know.

These are tracked as the agent-task-lifecycle follow-up to the local-directory work; until that ships, treat `local_directory` as "the agent runs in your folder, the same way you would."

## Attaching repos at project creation

In the **Web** or **Desktop** app, opening *New project* now shows a **Repos** pill alongside Status / Priority / Lead. Selecting workspace-bound repos (or pasting an ad-hoc URL) attaches them as `github_repo` resources the moment the project is created.

From the **CLI**:

```bash
# Create + attach in one shot. The server attaches resources in the same
# transaction as the project create — invalid resources roll back the whole
# operation, so you never end up with a project that has half its resources.
agora project create \
  --title "Agent UX 2026" \
  --repo https://github.com/jamshidtulaganov/agora

# Manage resources later
agora project resource list <project-id>
agora project resource add  <project-id> --type github_repo --url <url>
agora project resource remove <project-id> <resource-id>

# Generic escape hatch for any resource_type the server understands —
# no CLI change needed when a new type ships:
agora project resource add <project-id> \
  --type notion_page \
  --ref '{"page_id":"…","title":"…"}'
```

`--repo` may be repeated; each value is attached as a separate `github_repo` resource.

## What the agent sees at runtime

When the daemon spawns an agent for an issue inside a project, two things happen:

### 1. `.agora/project/resources.json`

A structured pass-through of the API response, written into the agent's working directory:

```json
{
  "project_id": "…",
  "project_title": "Agent UX 2026",
  "resources": [
    {
      "id": "…",
      "resource_type": "github_repo",
      "resource_ref": {
        "url": "https://github.com/jamshidtulaganov/agora",
        "default_branch_hint": "main"
      }
    }
  ]
}
```

Skills, helper scripts, or the agent itself can parse this file when they need the *exact* set of resources for the run.

### 2. A "Project Context" section in the meta-skill prompt

The agent's `CLAUDE.md` / `AGENTS.md` (depending on provider) now includes a human-readable summary:

```
## Project Context

This issue belongs to **Agent UX 2026**.

Project resources (also written to `.agora/project/resources.json`):

- **GitHub repo**: https://github.com/jamshidtulaganov/agora (default branch: `main`)

Resources are pointers — open them only when relevant to the task. For
`github_repo` resources, use `agora repo checkout <url>` to fetch the code.
```

The text is intentionally minimal. The full payload is on disk; the prompt only orients the agent so it knows the project exists and what's attached.

### Failure mode

Resource fetch is **best-effort**. If the API call fails, the project section is omitted from the prompt and the file is not written, but the task still starts. Agents never block on missing project context.

## Adding a new resource type

The whole point of the abstraction is that new types are cheap. The full path:

1. **Server validator** (`server/internal/handler/project_resource.go`) — add a case in `validateAndNormalizeResourceRef` that parses and normalizes the new payload.
2. **Daemon meta-skill formatter** (`server/internal/daemon/execenv/runtime_config.go`) — add a case in `formatProjectResource` so the agent prompt renders the new type as a readable bullet.
3. **TypeScript types** (`packages/core/types/project.ts`) — extend `ProjectResourceType` and add the payload interface.
4. **UI renderer** (`packages/views/projects/components/project-resources-section.tsx`) — add a case in `ResourceRow` for the new type.

There is **no schema migration**, no new sqlc query, no new endpoint, **and no CLI change** — the CLI's generic `--ref '<json>'` flag accepts any payload the validator understands, so day-one support for a new type is purely the four steps above. (You may *optionally* add a per-type CLI shortcut later; not required.)

The same `project_resource` table and the same three CRUD calls handle every type.

## Workspace repos vs. project repos

The repo list shown to the agent (`## Repositories` block in `CLAUDE.md` / `AGENTS.md`) is chosen by the daemon claim handler with this precedence:

- **Project has at least one `github_repo` resource** → only those repos are surfaced to the agent. Workspace-bound repos are intentionally hidden so the agent doesn't have to guess which one belongs to this issue.
- **Project has no `github_repo` resources (or the issue isn't in a project)** → fall back to the workspace's repo list as before.

This keeps the agent's working set tight: when a project is explicit about its repos, that's the authoritative answer. The structured resource list at `.agora/project/resources.json` always carries the full set, so a skill that wants to inspect everything still can.

The daemon mirrors this on the checkout side: when a task arrives with project-scoped `github_repo` URLs, those URLs are merged into the per-workspace allowlist *and* synced into the local repo cache before the agent spawns. So a project repo URL that isn't bound at the workspace level is still a valid argument to `agora repo checkout` — the daemon won't reject it as "not configured." The allowlist split is internal: workspace-bound URLs and task-scoped URLs are tracked separately, so a workspace-repos refresh doesn't accidentally revoke a project URL mid-run.

## What's intentionally **not** in scope here

- **Cross-project sharing.** Each resource lives on exactly one project today.
- **Per-skill resource scoping.** All resources are visible to every skill on the agent's run; type-aware filtering is a follow-up.
- **Caching / sync.** `github_repo` is just metadata — checkout still happens via `agora repo checkout` on demand. Cached document text for Notion / Google Docs will arrive with those types.

These are deliberate omissions — the goal of the first cut is to validate the abstraction with the smallest set of moving parts.
