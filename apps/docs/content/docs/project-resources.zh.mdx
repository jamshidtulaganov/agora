**项目资源（Project Resource）** 是挂在 [项目](/workspaces) 上的有类型的指针 —— 今天可以挂 GitHub 仓库 URL 或者本机的一个目录，未来还会有 Notion 页面、文档链接等等。当 [智能体](/agents) 在这个项目的 issue 上跑任务时，守护进程会自动把项目的资源列表写进智能体的工作目录，并塞进它的 [元 skill](/skills) prompt 里。

带来的结果：智能体知道应该 checkout 哪个仓库（或者在哪个本地目录里工作），知道项目"主要参考资料"是哪些 —— 没人需要把上下文复制粘贴进 issue 描述里。

## 心智模型

项目不再只是一个标签，而是一个小的 **资源容器**：

- 一个项目可以挂 0..N 个 **资源**。
- 每个资源有一个 `resource_type`（比如 `github_repo`、`local_directory`），以及一个 `resource_ref`（按 `resource_type` 定型的 JSON 负载）。
- 加新资源类型只需要加一个字符串 + 一个 handler。**不需要 schema 迁移，不需要重写前端。**

这个形状是有意的 —— 跟 Agora 里 agent provider 的设计完全一致：一个 `type` 判别字段 + 一个有类型的 payload。schema 保持稳定，未来加"Notion 页面"、"Google Doc"、"上传文件"、"外部 URL"都是小型的、增量的改动。

目前内置两种资源类型：[`github_repo`](#资源类型github_repo)（每次任务克隆出独立 worktree）和 [`local_directory`](#资源类型local_directory)（用某台守护进程机器上已经存在的目录 —— 原地跑，或者在从它切出的 worktree 里跑）。

## 资源类型：`github_repo`

默认的资源类型 —— 每次任务都在隔离的 worktree 里 checkout：

```json
{
  "resource_type": "github_repo",
  "resource_ref": {
    "url": "https://github.com/owner/repo",
    "default_branch_hint": "main"
  }
}
```

`default_branch_hint` 可选 —— 填了之后，守护进程会把它写进元 skill，告诉智能体该基于哪个分支干活。

## 资源类型：`local_directory`

对于那些不适合每次任务重新 clone 的仓库 —— 几十 GB 的游戏项目、超大 monorepo、或者本身就不想被多次复制的目录 —— 项目可以改为指向 **某台 [守护进程](/daemon-runtimes) 机器上的一个已有目录**。智能体默认会 **直接在这个目录里运行**，不 clone、不复制。

```json
{
  "resource_type": "local_directory",
  "resource_ref": {
    "local_path": "/Users/me/code/big-game",
    "daemon_id": "0001234e-…",
    "label": "主开发目录",
    "isolation": "in_place",
    "access": "write",
    "preview_url": "http://localhost:3000"
  }
}
```

必填的只有 `local_path` 和 `daemon_id`。另外三个是决定"智能体怎么用这个目录"的开关 —— [`isolation` 与 `access`](#智能体怎么用这个目录isolation-与-access)、[`preview_url`](#preview把-qa-指向你自己的开发服务器) —— 下面分别说明。

跟 `github_repo` 相比的取舍是有意的：只有绑定的那台守护进程会使用这个本地目录执行任务。换来的是：你的现有 checkout、当前分支、未提交的脏改动一切照旧 —— Agora 不会重新 clone。

### 什么时候选 `local_directory`、什么时候继续用 `github_repo`

| 关注点 | `github_repo`（worktree 模式） | `local_directory` |
| --- | --- | --- |
| 每次任务的 checkout 成本 | 重新 clone + worktree | 0 —— 代码本来就在那儿 |
| 同一仓库的并发 | 任意条任务并行 | `in_place` 串行；`isolation: worktree` 时按 issue 并行 |
| 分支 / 脏改动 | 每条任务从默认分支拉一个干净分支 | `in_place`：提交落在从你当前 HEAD 切出的隔离 `agent/…` 分支上，已跟踪的脏改动先快照。`worktree`：完全不碰你的 checkout |
| 可在哪台机器跑 | 任意守护进程 | 仅绑定的那一台 |
| 磁盘占用 | 每条任务一个 worktree | `in_place` 为 0；`worktree` 每个 issue 一个 |

一句话判断：**当代码已经在某台机器上、而"再取一次"才是最贵的那一步时，就用 `local_directory`** —— 或者你想让改动直接落在你已经打开的那个 checkout 里。

### 使用场景

下面是团队实际会用到的几种情况，以及每种该怎么配。

#### 1. 仓库太大，不适合每次任务重新 clone

几十 GB 的游戏 checkout、带大量 LFS 资源的 monorepo、`npm install` 要跑十分钟的项目 —— `git clone` 的耗时会盖过实际工作量。

用默认值（`in_place`、`write`）绑定你的 checkout。智能体就在你已有的目录里跑：不 clone、不复制、磁盘上也不会多出第二份资源。

#### 2. 想在自己的编辑器里盯着智能体干活

你在打磨某个组件，几分钟就要切回编辑器看一眼改了什么，而不想每次去 `~/agora_workspaces/` 翻一个新 worktree。

同样用默认值。智能体的提交落在从你 `HEAD` 切出的 `agent/…` 分支上，你的分支不会被移动，改动可以就地 review。

#### 3. 只读的参考代码库

一个老单体、一个厂商 SDK、一个你要对接的兄弟服务 —— 你希望智能体 **读懂** 这份代码，而不是改它。

设 **`access: read`**。目录会变成纯参考材料：智能体通过隔离 worktree 读取，所有写回你 checkout 的路径都被关闭。这比在 prompt 里写一句"别改这个目录"可靠得多。

#### 4. 一个 checkout 上同时推进多个 issue

三个智能体、三个 issue、一份本地仓库。默认的 `in_place` 会让它们互相排队 —— 正确，但慢。

设 **`isolation: worktree`**。每个 issue 拿到一个从你 checkout 切出的独立 worktree，于是 issue 之间并行，你的工作区也不被碰。

#### 5. 让 QA 测你已经跑着的那个应用

你的开发服务器已经在 `localhost:3000` 上，带着你正在调试的状态，你不想让 QA 再起第二个。

设 **`preview_url: http://localhost:3000`**。issue 的 Preview 面板会反代到你的服务器，reviewer 和 QA 智能体看到的就是你看到的那一个。

#### 6. 整个团队都在本地干活

一个共享项目，每个人都希望智能体跑在自己机器上。

每个人绑定 **自己的** `local_directory` —— 每台守护进程一条，各自指向各自机器上的路径。任务会落到"接收任务的那个智能体所属 runtime"的守护进程上，那台守护进程只挑 `daemon_id` 跟自己匹配的那一条。谁的目录都不会被别人的守护进程看到。

#### 什么时候 **不要** 用

如果你希望任意一台守护进程都能接这个活、而且 clone 成本不高，就继续用 `github_repo`。`local_directory` 会把工作绑死在一台机器上 —— 这正是它的意义，但机器休眠时这也是代价。

### 添加本地目录

三种方式，取决于你人在哪儿。三条路最后落到的是同一条资源记录 —— 手边是哪个就用哪个。

#### 网页端

打开项目 → **Resources（资源）** 面板 → **Add local folder（添加本地文件夹）**。

1. **Machine（机器）** —— 从工作区里在线的守护进程中，选代码所在的那台。（你无权使用的机器不会出现，见 [谁能挂载本地目录](#谁能挂载本地目录)。）
2. **Folder（文件夹）** —— 点 **Browse（浏览）** 走一遍那台机器的目录；如果你已经知道路径，直接填绝对路径也行。
3. **Access（权限）** —— *Read & write*（默认）或 *Read-only*，见 [`isolation` 与 `access`](#智能体怎么用这个目录isolation-与-access)。
4. **Preview URL** —— 可选，填你自己的开发服务器，比如 `http://localhost:3000`。
5. **Attach folder（挂载）**。

网页端挂载 **不会** 记录授权 —— 机主仍然要用 `agora daemon allow-dir` 授权这个路径，任务才能在里面跑。见 [机主授权](#机器上的机主授权)。

#### 文件夹浏览器

浏览器没法为 **另一台** 机器弹出 OS 文件夹选择器 —— 就算是本机，`<input type="file">` 也从不会把绝对路径交给 JavaScript。所以 **Browse** 改成让守护进程自己列目录，一层一层来：你走的是那台机器的真实目录，Agora 拿到的是真实路径。

你会看到：

- **只有文件夹**，因为你要挂载的就是文件夹。git 仓库会打上 **repo** 标记，一眼就能认出 checkout。
- **从机器的 home 目录开始**。可以往上走，但走到"这台机器愿意开放的顶层"就到头了。
- **只有机器愿意开放的部分**：守护进程只提供 home 目录，以及机主已经授权过的文件夹。其余一律拒绝 —— 所以选择器不可能被拿来翻一台机器的整块硬盘。
- **不会出现敏感目录**。凭据和系统目录 —— `~/.ssh`、`~/.aws`、`~/Library`、`AppData`、`$HOME` 下的点目录 —— 既不列出也打不开，所以列表里不会有点进去就报错的死路。

**浏览不等于授权。** 这个列表是只读的，本身不授予任何权限：在选择器里看得到某个文件夹，不代表智能体能在里面跑。授权是机主另外做的一个明确动作。

如果那台机器关着，选择器会直接告诉你，而不是一直转圈 —— 把它的守护进程起起来，或者先填路径挂上、之后再授权。

<Callout type="info">
文件夹浏览器要求那台机器的守护进程在 **v0.3.50 或更新** —— 列目录是守护进程自己提供的，不是后端。守护进程版本过旧时，浏览器会把错误直接显示在弹窗里；这时直接填路径，或者升级那台机器的 CLI。
</Callout>

#### 桌面端

打开项目 → **Resources（资源）** → **Add local directory（添加本地目录）**，会弹出原生文件夹选择器，绑定到 **当前这台桌面端注册的守护进程**。

选中文件夹的同时也会自动记录你的 **机主授权** —— 你人就在这台机器前，同意是隐含的。这是唯一一条"挂载 + 授权"一步完成的路径。

当本机守护进程离线、或者这个项目已经在本机绑定了一个 `local_directory` 时，按钮 **会置灰并给出一行说明** —— 让你看得到为什么暂时不能用。

#### CLI

适合无头机器、脚本，以及任何你已经 SSH 上去的机器：

```bash
agora project resource add <project-id> \
  --type local_directory \
  --local-path /Users/me/code/big-game \
  --daemon-id <daemon-uuid> \
  --ref-label "主开发目录"        # 可选

agora project resource update <project-id> <resource-id> \
  --local-path /Users/me/code/big-game-new
```

`--daemon-id` 可以通过 `agora daemon list` 拿到。CLI 也接受 `--ref '<json>'` 这种通用形式，直接传 payload —— 在命令行里设 `isolation`、`access`、`preview_url` 就靠它：

```bash
agora project resource add <project-id> \
  --type local_directory \
  --ref '{"local_path":"/srv/legacy","daemon_id":"<daemon-uuid>","access":"read","isolation":"worktree"}'
```

### 谁能挂载本地目录

`local_directory` 的增删改 **只允许人类操作**。用机器凭证 —— 智能体的 task token、或者云节点的 PAT —— 发起的任何 `local_directory` 创建、更新、删除都会被 `403` 拒绝，连"创建项目时顺带打包资源"的路径也一样。智能体永远无法把自己（或别的智能体）绑到你机器上的某个文件夹；如果一条任务确实需要本地目录，智能体应该请你自己去挂。`github_repo` 资源不受影响 —— 智能体照常可以在仓库引导流程里创建它们。

`daemon_id` 会在挂载时校验一次，之后每次 `resource_ref` 变更时再校验一次：

- 它必须对应一个 **已在工作区注册** 的守护进程运行时 —— 不存在或者打错的守护进程 ID 会被 `400` 拒绝。
- 这个运行时必须是 **你有权使用的**：你是它的 owner、它是共享的（`visibility=public`）、或者你的角色是 workspace owner/admin。把资源指向别的成员私有的守护进程会被 `403` 拒绝。

这跟"把智能体绑到某个运行时"用的是同一套所有权规则，只是套在了目录所在的那台机器上。

### 机器上的机主授权

光把资源挂上还不够：**目录所在机器的机主必须先在那台机器上授权这个文件夹**，守护进程才会在里面跑任务。资源行存在服务器上，任何拿到你工作区凭证的人都能创建它 —— 而授权存在执行任务的机器本地，只有机主本人能写入。授权有三种方式：

- **桌面端文件夹选择器** —— 选中文件夹的动作本身就会自动记录授权。正常流程里你完全不用管这一步。
- **`agora daemon allow-dir <path>`** —— 在守护进程所在主机、以守护进程运行的那个 OS 用户身份执行。授权保存在 `~/.agora/local-dirs.json`，每次任务都会重新读取，不需要重启守护进程。
- **`AGORA_LOCAL_DIR_ALLOWLIST`** —— 以路径列表分隔符拼接的绝对路径列表，供无界面或容器化的守护进程使用（那里既没有选择器也没法跑 CLI）。

授权一个文件夹即覆盖它下面的全部内容。任务指向未授权的路径时会快速失败，错误信息里直接给出要执行的 `allow-dir` 命令 —— 授权后重新派发即可，不需要清理任何东西。

**从网页端或 CLI 挂载的资源，总是需要手动授权一次**，因为守护进程主机上没有跑过选择器。用网页端 [文件夹浏览器](#文件夹浏览器) 找到的文件夹同样如此：浏览只是只读列目录，不授予任何权限。这个拆分是刻意的 —— 挂载是任何拿到你工作区凭证的人都能做的动作，而授权是坐在那台机器前的人做的本地决定。只有桌面端把两者合并成一步，因为在那里这两个人就是同一个人。

在守护进程主机上用 `agora daemon list-dirs` 查看已授权的目录（区分文件和环境变量来源），用 `agora daemon revoke-dir <path>` 移除一条文件授权（环境变量授权通过取消设置 `AGORA_LOCAL_DIR_ALLOWLIST` 来撤销）。

### 智能体怎么用这个目录：`isolation` 与 `access`

两个字段决定智能体能拿你的 checkout 做什么。两者的默认值都等于最初的行为，所以在它们出现之前挂的资源不受影响、照常工作。

**`isolation`** —— 智能体的工作树从哪儿来：

| 取值 | 行为 | 什么时候用 |
| --- | --- | --- |
| `in_place`（默认） | 智能体 **直接在你的目录里** 干活。提交落在从你 `HEAD` 切出的隔离分支 `agent/<name>/<task>` 上，你的分支 ref 不会被移动。同一目录上的任务 **每次只跑一条**。 | 你想让改动直接落在你已经打开的那个 checkout 里。 |
| `worktree` | 智能体在 **从你 checkout 切出的独立 git worktree** 里干活，worktree 放在 `~/agora_workspaces/<ws>/.worktrees/<issue>/` —— 在你的目录之外。你的工作树完全不被碰。每个 issue 一个 worktree，并在该 issue 的 dev → QA → 修复任务之间复用，所以 **不同 issue 之间并行**。 | 一个 checkout 上同时推进多个 issue，或者你希望自己的工作树完全不被动。 |

**`access`** —— 智能体被允许做什么：

| 取值 | 行为 |
| --- | --- |
| `write`（默认） | 智能体可以修改这个目录 —— 原地编辑，或者 worktree 写回。 |
| `read` | 目录是 **纯参考材料**。所有写回你 checkout 的路径都被关闭，智能体通过一个游离（detached）worktree 读取它。 |

`access: read` 会 **强制 `isolation: worktree`** —— 原地运行本身就是一种写入。API 会用 `400` 拒绝 `read` + `in_place` 的组合，而不是悄悄"帮你修正"；即便一条旧的 ref 混了进来，守护进程也会强制走 worktree 模式。所以只读目录不可能被原地交给智能体。

在网页端，这两个开关就是挂载表单和每条资源行上的 **Read & write / Read-only** 切换。把某一行切成 *Read-only* 时，它会同时切到 worktree 隔离。

<Callout type="warning">
没有文件级的写入锁。对 `in_place` 来说，"同一目录每次一条任务"这道串行闸是唯一防止两个 issue 的智能体同时改同一份文件的保护。如果你需要在同一个 checkout 上真正并行，请用 `isolation: worktree`（每个 issue 一棵独立的树），而不是把两个 issue 指向同一个原地目录。
</Callout>

### Preview：把 QA 指向你自己的开发服务器

`preview_url` 就是你 **自己本地跑着的那个开发服务器** —— 你干活时本来就开着的那个：

```json
"preview_url": "http://localhost:3000"
```

填了之后，issue 的 **Preview** 面板会反代到那个服务器，而不是自己再起一个。reviewer 和 QA 智能体看到的就是你看到的那个应用、那个状态 —— 不用起第二个服务器，也不用等构建。

- 只接受 `localhost`、`127.0.0.1`、`::1` 和内网私有地址。是 **守护进程** 去连你的服务器，不是公网 —— 这个 URL 从外部根本不需要可达。
- 留空则 Preview 退回到自己启动项目的开发服务器（检测逻辑见 [在本地目录上做 QA](#在本地目录上做-qa)）。
- 网页端点资源行上的 **屏幕图标** 设置；CLI 用 `--ref` 设置。

打开 Preview 时如果你的服务器没在跑，面板会直接说连不上 —— 不会在你背后偷偷启动任何东西。

### 路径规则

挂资源时和每次任务启动时，守护进程都会校验一次路径（服务器负责校验"谁在挂、挂到哪台守护进程"，见上一节，但不检查路径本身）。任何一条不满足的，任务会以一个有类型的错误失败，**不会动你的目录**：

- 必须是 **绝对路径**。
- 必须 **存在**，并且是 **目录**（不能是普通文件、设备节点、或者指向文件的 symlink）。
- 守护进程进程必须能 **读 + 写**。
- 不能是系统根目录或整个用户配置区 —— `/`、`/Users`、`/home`、`/root`、`/etc`、`/tmp`、`/var`、`/usr`、`/opt`、`/Users/Shared`、你自己的 `$HOME`、任意 Windows 盘根（`C:\`、`D:\`…），以及 `C:\Users` / `C:\ProgramData` / `C:\Program Files` / `C:\Program Files (x86)` / `C:\Windows`。
- 不能位于 **受保护的 home 子树** 里：`$HOME` 下直接的任何点目录（`~/.ssh`、`~/.aws`、`~/.gnupg`、`~/.config`……）、macOS 的 `~/Library`、Windows 的 `AppData`。这些地方放的是凭证和系统状态，从来不是项目 —— 而智能体是在关闭所有权限确认的模式下运行的，把这样的目录交给智能体等于交出整个凭证库。
- 指向上述任何路径的 symlink 也会被拒；macOS 的 canonical 别名（比如手动输入 `/private/tmp`）和 `/tmp` 受同样的限制。

黑名单故意做得激进 —— 选你自己的 home 目录就意味着 Agora 的运行时文件会出现在你账号的根下，这不会是任何人想要的结果。请选一个子目录（一般就是你具体的项目 checkout）。

### 每台守护进程每个项目最多一条

同一项目上 **每台守护进程最多只能绑一个 `local_directory`**。在同一台机器上想再加一条会被 API 用 `409` 拒绝。两端都会提前把这个限制表达出来，而不是让你以报错的形式发现：桌面端的按钮会置灰并说明原因，网页端的机器选择器则不再列出那台"在这个项目上已经有文件夹"的机器。

不同的守护进程互不影响 —— 一个共享的项目可以为每个队友的机器各绑一个 `local_directory`，把同一个项目挂到不同主机上的不同目录。守护进程领任务时会挑跟自己 ID 匹配的那一行，其它的忽略。

### 混用资源类型，以及多个 `local_directory` 资源

实际会碰到两种跨资源的组合：

- **同一个项目同时挂 `github_repo` 和 `local_directory`。** 在拥有匹配 `local_directory` 绑定的那台守护进程上，本地目录 **优先**：智能体跑在你的目录里，这次任务不会为项目的 `github_repo` 创建或使用 worktree。智能体的 brief 也会改写成 in-place 模式 —— 不再给它 "`agora repo checkout <url>`" 的指引，而是一个 **Working Directory (local, in-place)** 段，告诉它代码已经在这里、直接编辑文件，**不要** 运行 `agora repo checkout`（那会在你的文件夹里嵌套一个多余的 worktree）。`github_repo` 的 URL 仍会在 `.agora/project/resources.json` 和 brief 里列出供参考，并标注"已由你所在的目录代表 —— 不要 checkout"。在 **没有** 匹配 `local_directory` 行的其他守护进程上（不同机器、或者那位队友还没挂本地目录），任务按原本的 `github_repo` worktree 流程走。本质上 `local_directory` 是某台守护进程对 worktree 路径的一个覆盖。
- **同一个项目挂两个 `local_directory`。** 每个 `local_directory` 只能绑一台守护进程，所以这只会发生在两台不同机器之间（同一台机器上想加第二条会被 API 当场拒掉，见上一节）。任务的去向由智能体 runtime 绑定决定，不是由"哪台守护进程有本地目录"决定 —— 任务会落到承载这条智能体 runtime 的那台守护进程上，由它挑出匹配自己 ID 的那一行、忽略其他行。这里没有负载均衡：如果你想让某台机器跑某条任务，请把任务派给绑在那台机器 runtime 上的智能体。

如果某台守护进程没有匹配这个项目的 `local_directory` 行，**不会**因为别处有人绑了就被拦下 —— 它的任务会照常走项目里的其他资源（一般就是 `github_repo` 那条 fallback 路径）。`local_directory` 只对它绑定的那台守护进程生效。

### 任务在本地目录里如何运行

当一条任务被分发到某个 issue、并且该项目在领任务的守护进程上绑了 `local_directory` 时，守护进程会：

1. 再次校验路径（按上面那套规则）。
2. 以 symlink 解析后的真实路径为 key 取一把"目录锁" —— 即便两条路径走不同路由（一条经过 symlink，一条直接）指向同一个文件夹，也会被串行化。
3. 把智能体的 `CLAUDE.md` / `AGENTS.md`（以及 `.agora/project/resources.json`）**写进你的目录**。智能体就在那里工作，跟你自己打开这个文件夹后启动它是一样的体验。
4. Agora 自己的运行时产物（`output/`、`logs/`、`.gc_meta.json`）放在 **你目录之外** 的一个独立 envRoot 里。

如果第一条任务还在跑、第二条针对同一目录的任务又来了，第二条会停在 **Waiting for local directory（等待本地目录释放）** 状态。这个状态在所有相关 UI 都看得见 —— 聊天里的任务状态条、智能体横幅、执行记录、活动指示器；等待中的任务会被计入该智能体的"排队"占用。取消等待中的任务会立即释放它的槽位；取消正在跑的那条会让下一条立即顶上。

等待没有超时 —— 一条等待中的任务会一直等到锁释放、或者被用户/智能体取消为止。

### Agora 会写、不会动什么

- **会写入** `CLAUDE.md` / `AGENTS.md`（或对应 provider 的等价文件）以及 `.agora/project/resources.json` 到目录根 —— 这样智能体才有自己的元 skill 和资源清单。如果不想把这些提交到 git，请加进 `.gitignore`。
- **会写入** 智能体决定做出的所有代码改动 —— 跟你自己在本地跑这个智能体没有区别。
- **永远不会物理删除** 你的目录或里面任何内容。垃圾回收对路径是有判断的：对 `local_directory` 的 envRoot，它只会清自己挂在 `workspacesRoot` 下的 `output/` 与 `logs/`，**完全不碰** 你的目录。

### Git 安全（当目录是 git 仓库时）

如果这个文件夹是 git 工作树，守护进程会自动保护你的分支和未提交的工作：

- **你的提交始终归你。** 智能体运行前，守护进程会从你当前的 `HEAD` 创建一个隔离分支 `agent/<智能体名>/<短任务 id>` 并切过去。智能体的提交落在这个分支上，绝不会落到你的分支上。你的分支 ref 从头到尾不会被移动。
- **只读运行不留痕迹。** 如果智能体没有产生任何提交（QA 门禁、纯查看），任务结束时守护进程会删掉那个分支、把你切回原来的分支 —— 仓库和你离开时一模一样。
- **智能体真的提交了，就把你留在 agent 分支上**，方便你就地 review。任务的结果评论里会写清分支名和切回去的一行命令（`git checkout <你的分支>`）。切回去这一步有意留给你自己 —— 一次真实运行之后，守护进程绝不会在你脚下改写工作树文件。
- **脏改动会被备份。** 智能体启动时如果你的工作树有未提交的 **已跟踪** 改动，守护进程会用 `git stash create` 把它们快照到 `refs/agora/backup/<短任务 id>` —— 这是一次零改动的备份，不会移动任何文件。用 `git stash apply <ref>` 恢复（恢复命令会打印在结果评论里）。**未跟踪** 文件不在这个快照里。
- 纯（非 git）文件夹跳过上述全部，照旧就地运行。

### 在本地目录上做 QA

当工作区开启了 `labs.qa_dev_runtimes` 时，自动 QA 门禁（issue 进入 `in_review` 时触发）知道怎么测一个只存在于你本地文件夹里的应用：

- **QA 任务跑在你的机器上。** 如果 issue 所在项目有一个绑到在线守护进程的 `local_directory`，门禁会把 QA 任务钉到那台守护进程上 —— 只有那里才能访问到应用的 `127.0.0.1`。它的优先级低于一个已声明的 `dev_apps` 具体 URL，但高于已部署的 QA box。
- **应用会替你启动。** QA 智能体通过守护进程的开发服务器 preview 把应用拉起来（和"Preview"一节里的探测是同一套），然后 smoke 得到的 `http://127.0.0.1:<port>/`。如果应用需要特定的启动命令，设置项目的 QA smoke 命令。
- **QA 绝不动你的工作树。** QA 智能体被明确要求不得在你的文件夹里切分支或改文件；它会在旁边用一个一次性的 `git worktree` 建立对比基线。配合上文的 git 安全分支处理，一次 QA 运行结束后你的工作目录和原来一模一样。
- **它会排在你自己的任务后面。** 因为同一个文件夹上的任务是串行的，QA 门禁会等你在同一目录上进行中的开发任务跑完再运行 —— 在拿到锁之前你会看到 `waiting_local_directory`。

想实时观看 QA 智能体驱动浏览器，需要后端能访问到你的守护进程（自托管，或笔记本已接入 mesh）。云端后端实时观看笔记本上的应用是另一套 mesh 配置。

### v1 阶段的限制（后续会逐步收敛）

第一版有意比 `github_repo` 留了更多锋利的边。下面这份清单会随着后续工作逐步缩短；这里列出的是 **今天**的真实行为：

- **未跟踪文件不进快照。** 脏改动备份只抓已跟踪的修改；智能体如果覆盖或删除了一个未跟踪文件，就没有东西可恢复。重要的未跟踪工作请在有风险的运行前先 commit 或 stash。（这条针对 `in_place`；用 `isolation: worktree` 时智能体根本不在你的工作树里干活。）
- **有提交的运行结束后你会停在 agent 分支上。** 守护进程不会自动把你切回去（那会改写你的工作树）。结果评论里给了切回去的命令。
- **不会自动开 PR。** 任务结束后，改动停在 agent 分支上 —— Agora 不会 push、不会开 PR。需要 push、需要 PR 的话请自己来。
- **`waiting_local_directory` 只显示状态，不显示是谁占着。** 这个徽标只告诉你"任务在等"，不会告诉你具体是哪条任务、哪个路径正在持有目录。
- **文件夹浏览器只能走，不能搜。** 没有搜索框，也没有"最近使用的文件夹" —— 要么一层层走，要么直接粘贴你已经知道的路径。

这些都列在 local-directory 工作的"智能体任务生命周期"后续项里；在那之前，请把 `local_directory` 当作"智能体在你的目录里跑，跟你自己跑没区别"来用。

## 在创建项目时挂仓库

在 **网页端** 或 **桌面端**，打开 *新建项目* 时，Status / Priority / Lead 旁边多了一个 **Repos** 标签。选已绑到工作区的仓库（或者粘贴一个临时 URL），项目创建的瞬间它们就以 `github_repo` 资源的形式挂上去。

通过 **CLI**：

```bash
# 创建 + 挂资源一步到位。资源是在同一个事务里挂上的 ——
# 任何一个资源不合法都会让整个 create 回滚，绝不会出现
# "项目建好了但资源只挂了一半"的状态。
agora project create \
  --title "Agent UX 2026" \
  --repo https://github.com/jamshidtulaganov/agora

# 后续管理资源
agora project resource list <project-id>
agora project resource add  <project-id> --type github_repo --url <url>
agora project resource remove <project-id> <resource-id>

# 任何服务器认识的 resource_type 都可以用这个通用入口 ——
# 加新类型时不需要改 CLI：
agora project resource add <project-id> \
  --type notion_page \
  --ref '{"page_id":"…","title":"…"}'
```

`--repo` 可以重复指定；每个值会被当作一条单独的 `github_repo` 资源挂上去。

## 运行时智能体看到什么

当守护进程为一个项目内的 issue 启动智能体时，会发生两件事：

### 1. `.agora/project/resources.json`

API 响应的结构化透传，写进智能体的工作目录里：

```json
{
  "project_id": "…",
  "project_title": "Agent UX 2026",
  "resources": [
    {
      "id": "…",
      "resource_type": "github_repo",
      "resource_ref": {
        "url": "https://github.com/jamshidtulaganov/agora",
        "default_branch_hint": "main"
      }
    }
  ]
}
```

Skill、辅助脚本、或者智能体自己想拿到本次运行**精确的**资源列表时，解析这个文件即可。

### 2. 元 skill prompt 里的 "Project Context" 段

智能体的 `CLAUDE.md` / `AGENTS.md`（按 provider 不同）里多出一段人类可读的摘要：

```
## Project Context

This issue belongs to **Agent UX 2026**.

Project resources (also written to `.agora/project/resources.json`):

- **GitHub repo**: https://github.com/jamshidtulaganov/agora (default branch: `main`)

Resources are pointers — open them only when relevant to the task. For
`github_repo` resources, use `agora repo checkout <url>` to fetch the code.
```

这段文字故意做得很精简：完整 payload 已经写到磁盘上了，prompt 只是给智能体一个定位 —— 让它知道项目存在、知道挂了什么。

### 失败时

资源拉取是 **best-effort**。如果 API 调失败了，prompt 里的项目段会省掉、文件也不写，但任务照常启动 —— 智能体永远不会因为缺少项目上下文而卡住。

## 加一种新资源类型

抽象的全部目的就是让加新类型变便宜。完整流程：

1. **服务端校验器**（`server/internal/handler/project_resource.go`）—— 在 `validateAndNormalizeResourceRef` 里加一个 case，解析并标准化新的 payload。
2. **守护进程元 skill 格式化器**（`server/internal/daemon/execenv/runtime_config.go`）—— 在 `formatProjectResource` 里加一个 case，让智能体 prompt 把新类型渲染成一条可读的列表项。
3. **TypeScript 类型**（`packages/core/types/project.ts`）—— 给 `ProjectResourceType` 加值，并加上对应的 payload 接口。
4. **UI 渲染**（`packages/views/projects/components/project-resources-section.tsx`）—— 在 `ResourceRow` 里加一个 case 渲染新类型。

**不需要 schema 迁移、不需要新的 sqlc query、不需要新的 endpoint、也不需要改 CLI** —— CLI 的通用 `--ref '<json>'` 选项接受校验器认识的任何 payload，第 0 天就能用。（之后如果想加按类型的 CLI 快捷参数，可以加，但不是必须。）

同一张 `project_resource` 表、同一套 CRUD 调用，处理所有类型。

## 工作区仓库 vs. 项目仓库

智能体看到的仓库列表（`CLAUDE.md` / `AGENTS.md` 里的 `## Repositories` 段）由守护进程的领任务逻辑按以下优先级决定：

- **项目挂了至少一条 `github_repo` 资源** → 仅显示项目挂的仓库。工作区绑定的仓库会被隐藏，避免智能体猜哪一个属于这个 issue。
- **项目没挂 `github_repo` 资源（或 issue 根本不在项目里）** → 回落到工作区的仓库列表，跟以前一样。

这样可以把智能体的工作集压紧：项目把仓库说清楚了，那就是权威答案。而 `.agora/project/resources.json` 里始终带着完整列表，需要查看全部资源的 skill 仍然能拿到。

守护进程在 checkout 这一侧也是配套的：当任务带着项目级别的 `github_repo` URL 进来时，这些 URL 会被合并进每工作区的白名单，并在智能体启动前同步进本地仓库缓存。所以即便某个项目仓库 URL 没被绑到工作区，`agora repo checkout` 也能正常处理它，不会以"未配置"为由拒绝。白名单的划分只是内部实现：工作区绑定的 URL 和任务级别的 URL 分开记录，工作区仓库列表的刷新不会顺手吊销某条项目 URL。

## 当前**不**做的事

- **跨项目共享**。每条资源现在只能挂在一个项目上。
- **按 skill 划定资源可见性**。所有资源对智能体本次运行里的每个 skill 都可见；按类型过滤是后续工作。
- **缓存 / 同步**。`github_repo` 目前只是元数据 —— checkout 仍然按需走 `agora repo checkout`。Notion / Google Docs 之类的文档文本缓存会随对应类型一起到位。

这些是有意的留白 —— 第一版的目标是用最小的活动部件去验证这个抽象。
