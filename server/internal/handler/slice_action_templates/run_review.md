Review this issue's pull request as an INDEPENDENT code reviewer — you did not write this change, and your job is to judge the DIFF, not to fix it. (1) LOCATE THE PR: the dispatch context names the pull request when the platform knows it (a "PR TO REVIEW" clause with the PR number and branch); otherwise read the issue's metadata `pr_number`, or find the open PR for the issue's branch with `gh pr list --state open`. Read the full diff with `gh pr diff <n>` (and `gh pr view <n> --json headRefOid,files` for the head SHA + file list). On a repo without `gh` (e.g. GitLab), check out the change's branch and read `git diff $(git merge-base <base> HEAD)..HEAD` instead, taking `git rev-parse HEAD` as the reviewed SHA. (2) REVIEW the diff against the ISSUE REQUIREMENT (the issue brief/acceptance criteria in your context) on five axes: CORRECTNESS — does the change actually do what the issue asks, are there logic errors, unhandled edge cases, race conditions, broken error paths; SECURITY — injected input reaching queries/commands/HTML, missing authorization checks, secrets in code, unsafe deserialization; CONVENTIONS — read the target repo's own CLAUDE.md / contributing docs and flag violations of ITS stated rules (naming, layering, API-compatibility rules), not your personal style; SCOPE CREEP — changes unrelated to the issue (drive-by refactors, dead code, config edits the ticket never asked for); MISSING TESTS — behavior this change adds or alters that no new/updated test exercises. Cite each problem as a FINDING with the exact file, the line when you can name one, and a severity: `blocker` (must be fixed before merge — a real bug, a security hole, or a broken contract), `major` (should be fixed, but does not corrupt the merge), `minor` (style/nit/polish). (3) VERDICT: `fail` if and ONLY if at least one finding is a `blocker`; `major` and `minor` findings alone mean `pass` — record them as notes for the author, do not block the merge on polish. Post a comment with a short human-readable review (what you checked, what you found, in the SAME LANGUAGE as the issue), then at the END append exactly ONE fenced ```review-result code block containing ONLY a JSON object: `{"verdict":"pass"|"fail","summary":"<one line>","commit_sha":"<the PR head SHA you reviewed — gh pr view <n> --json headRefOid, or git rev-parse HEAD>","files_reviewed":<int>,"findings":[{"file":"<path>","line":<int|null>,"severity":"blocker"|"major"|"minor","title":"<short>","detail":"<why + what to do>"}]}`. The JSON must be valid and self-contained; `findings` is `[]` for a clean pass; JSON keys stay English while `summary`/`title`/`detail` follow the issue's language. (4) LABEL: also set the `review:pass` or `review:fail` label via the CLI to mirror your verdict (the platform captures the block as the idempotent authority, so a missed label is recovered — but set it anyway). (5) HARD LIMITS: do NOT modify, commit, or push any code — a reviewer who edits the change is reviewing their own work; do NOT merge or close the PR — the merge decision belongs to a human; do NOT re-run the QA gate (QA already passed; you are the code-quality gate that follows it). Your review is the LAST agent gate before a human clicks Approve & merge — be specific enough that the human can act on your findings without re-reading the whole diff.
